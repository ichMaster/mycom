## Findings

### 1. 🔴 HIGH — An uncaught `OSError` during any file operation crashes the whole app

**Failure scenario:** Select 50 files to copy; file #30 has a permission the user doesn't own
(EACCES) — or the destination filesystem runs out of space (ENOSPC) — or a file in the batch is
deleted by another process between listing and copying (ENOENT). `copy_entry`/`move_entry`/
`delete_entry` raise a plain `OSError` for all of these. None of `action_copy`'s, `action_move`'s,
`action_delete`'s, or `action_rename`'s worker closures (`mycom/app.py`, the four `worker()`
closures inside `_run_copy`/`_run_move`/`_run_delete`/`_run_rename`) catch anything broader than
`ConflictTypeMismatchError`. `_run_delete`'s worker catches nothing at all.

Textual's `Worker._run()` (`.venv/.../textual/worker.py:373-383`) defaults every `run_worker(...,
thread=True)` call to `exit_on_error=True`: an uncaught exception in the worker sets
`self._error` and calls `app._handle_exception(worker_failed)` — which tears down the whole
running app. So the realistic outcome of a mid-batch permission error isn't a stuck progress
dialog (the milder failure I originally suspected) — it's the entire TUI exiting, discarding
whatever the user was doing in either panel. This directly contradicts the project's own
established graceful-degradation posture (`action_quit`'s wrapped flush, `StateDB.__init__`'s
try/except, `refresh_listing`'s `except OSError`, `_prompt_mkdir`'s `except (OSError,
ValueError)`) — the v0.4 workers are the one place that pattern wasn't carried through.

A second, narrower instance of the same gap: `_run_copy`, `_run_move`, and `_run_rename` call
`build_plan`/`stat()` **synchronously on the main thread**, before any worker is spawned (e.g.
`_run_rename`'s `src.stat()` for a file size, `build_plan`'s per-entry `source.stat()` while
walking). A source vanishing between "user confirms the dialog" and "the plan is built" (a narrow
but real TOCTOU window) raises the same uncaught `OSError`, this time outside a worker entirely —
same crash, different call site.

**Proposed fix:** Add a shared `_show_operation_error(progress_dialog, message)` helper (dismiss
the progress dialog if one exists, show an `ErrorDialog`, refresh both panels) and:
- wrap each worker's `execute_*` call in `except OSError as exc:` alongside the existing
  `ConflictTypeMismatchError` handling, routing to the shared helper;
- wrap `_run_copy`/`_run_move`/`_run_rename`'s plan-building body (before the worker is spawned)
  in the same `except OSError`, so a vanished-source race shows a clean error instead of an
  unhandled crash.

### 2. 🟡 LOW — Cancelling a copy/move mid-file leaves a partial destination file

**Failure scenario:** Copying a large file, the user cancels while it's mid-chunk. `copy_entry`
raises `OperationCancelledError` from inside the `with open(... ) as fsrc, open(...) as fdst:`
block, having already written some chunks to `fdst`. That partial file is never removed. The
*source* is always safe (copy never touches it, and move only unlinks the source after full
copy+size-verification) — so this doesn't violate v0.4's DoD ("already-copied files intact and
source untouched") or any tested acceptance criterion. But a user who cancels then retries the
same copy will see an unexpected conflict prompt for the truncated leftover, rather than a clean
slate.

This is standard behavior for most file managers (`cp`, Finder, Explorer all leave partial files
on an interrupted copy) and cleaning it up is a reasonable but separate piece of resilience work —
it overlaps with the recovery-policy machinery `spec/architecture.md` already earmarks for v1.3
(`RecoveryPolicy`: Retry/Skip/Skip All/Cancel on *errors*, layered on the same engine). Deferring
rather than bolting an ad-hoc partial-file cleanup onto `copy_entry` now.

**Proposed fix (deferred):** When `OperationCancelledError` is raised mid-file, delete the
partially-written `entry.dst` before propagating, or fold this into v1.3's recovery-policy work
so cleanup-on-cancel and cleanup-on-error share one mechanism.

## What's solid

- The plan/policy/progress seams (`PlanEntry`, `OpPlan`, `ConflictChoice`, `ConflictPolicy`,
  `OpProgress`, `CancelToken`) are clean, fully synchronous, and unit-tested independent of
  Textual — exactly the shape `spec/architecture.md` calls for.
- Cross-device move's verify-before-delete ordering is correct and well-tested (`move_entry`
  never unlinks the source until the destination's size is confirmed to match).
- The same-file guard (`copy_entry` raising `shutil.SameFileError` when src/dst resolve to the
  same file) closes a real truncation risk before it could ever ship.
- The `DialogKit._on_escape()` hook (added mid-phase, MC-026) is a correct, minimal fix for a
  genuine Textual dispatch quirk (every MRO class defining `on_key` runs, not just the
  most-derived one) — and it retroactively fixed a real pre-existing bug in `ProgressDialog`.
- `ConflictDialogPolicy`'s thread-marshalling (`call_from_thread` + a manually-resolved
  `asyncio.Future`, since `push_screen_wait` needs an active Worker context a plain
  `call_from_thread` coroutine doesn't have) was verified against a live, non-mocked
  cross-thread run before being wired into any action — not just assumed correct.
- Selection order (`get_selected_files()`) is sorted, so multi-file operation order — and thus
  "what survives a mid-operation cancel" — is deterministic and testable, not hash-order noise.
- The delete confirmation ladder (initial → per-non-empty-dir → per-read-only-file) and the
  cursor-survivor logic (skips past rows that are themselves being deleted) both handle their
  respective edge cases correctly, with real filesystem-permission fixtures in tests, not mocks.

## Fixes applied

### #1 — uncaught `OSError` crashing the app

**Commit:** 5e19fbc

**Change:** Added a shared `MyComApp._show_operation_error(progress_dialog, message)` helper
(dismiss the progress dialog if one exists, show an `ErrorDialog`, refresh both panels) and:
- wired `except OSError as exc:` alongside the existing `ConflictTypeMismatchError` handling in
  all four worker closures (`_run_copy`, `_run_move`, `_run_delete`, `_run_rename`) — `_run_delete`
  previously had no exception handling at all;
- wrapped the main-thread plan-building calls that run *before* any worker is spawned
  (`build_plan` in `_run_copy`/`_run_move`, `build_delete_plan` in `_confirm_next_nonempty_dir`,
  the `src.stat()`/`is_dir()`/`is_symlink()` calls in `_run_rename`) in the same `except OSError`,
  closing the narrower TOCTOU window (a source vanishing between confirming a dialog and the plan
  actually being built);
- consolidated the three near-duplicate `_finish_copy_error`/`_finish_move_error`/`_rename_error`
  methods into the one shared helper, and added a small `_type_mismatch_message(verb, exc)` helper
  to keep the `ConflictTypeMismatchError` message consistent across all four actions.

**Regression test:** One test per action —
`test_f5_unexpected_os_error_shows_error_dialog_not_a_crash` (`test_copy_keys.py`),
`test_f6_unexpected_os_error_shows_error_dialog_not_a_crash` (`test_move_keys.py`),
`test_f8_unexpected_os_error_shows_error_dialog_not_a_crash` (`test_delete_keys.py`),
`test_shift_f6_unexpected_os_error_shows_error_dialog_not_a_crash` (`test_rename_keys.py`) — each
monkeypatches the relevant `mycom.app.execute_*` function to raise a plain `OSError`, drives the
action through the real UI, and asserts an `ErrorDialog` appears and the app remains alive and
responsive afterward (screen stack back to 1, ready for the next keypress) rather than exiting.

**Verification:** `pytest` — 302 passed (4 new regression tests). `ruff check` — clean.

**Architecture impact:** None — no seam/contract changed; this is purely an error-handling
completeness fix inside `mycom/app.py`'s existing action-wiring layer. No `spec/architecture.md`
update needed.
