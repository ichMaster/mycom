## v0.4 — File operations

### MC-025 — Operation engine core: plan/execute/progress/cancellation (+ dead-scaffold cleanup)

**Description:**
The plan → execute pipeline every file operation (copy/move/delete) builds on:
`spec/architecture.md`'s `fileops/` package. Pure Python, no Textual dependency — fully
unit-testable against tmpfs fixtures. Also removes the two empty pre-pivot scaffolds
`spec/architecture.md`'s migration note already calls out as dead.

**What needs to be done:**
- Delete `mycom/llm/` and `mycom/plugins/` (and their `__init__.py`/subpackages) — confirmed empty
  scaffolds, no test imports them (verify with `grep -rn "mycom.llm\|mycom.plugins" mycom/ tests/`
  before deleting).
- `mycom/fileops/plan.py`: `PlanEntry` (frozen dataclass: `src: Path`, `dst: Path`, `is_dir: bool`,
  `is_symlink: bool`, `size: int`) and `OpPlan` (`entries: tuple[PlanEntry, ...]`, `total_bytes:
  int`, `total_files: int` — files only, dirs don't count toward the file total).
  `build_plan(sources: list[Path], dest_dir: Path) -> OpPlan`: walks each source (a lone file is
  one entry; a directory recurses, preserving its subtree under `dest_dir/source.name/...`);
  symlinks are **not** followed during the walk (recorded as `is_symlink=True` leaf entries, not
  recursed into). Does **not** itself refuse self-copy/into-own-subdirectory — that's a
  precondition check the caller (MC-027) runs before planning, since it's specific to "is any
  source an ancestor of dest_dir", not a planning concern.
- `mycom/fileops/policy.py`: `ConflictChoice` enum (`OVERWRITE`, `SKIP`, `RENAME`,
  `OVERWRITE_ALL`, `SKIP_ALL`, `CANCEL`); a `ConflictPolicy` protocol/callable type
  `(PlanEntry, existing_dst_stat) -> ConflictChoice | tuple[ConflictChoice, Path]` (the `Path`
  variant carries a `RENAME` choice's new target) that MC-026's dialog implements and tests can
  fake; "All" choices are the injected policy's own responsibility to remember for the rest of one
  call — the engine just asks again for every conflict and trusts the answer.
- `mycom/fileops/engine.py`: `OpProgress` (frozen dataclass: `current_file: str`,
  `bytes_done: int`, `bytes_total: int`, `files_done: int`, `files_total: int`, `speed_bps:
  float`, `eta_seconds: float | None`); a `CancelToken` (thin wrapper over `threading.Event`);
  `copy_entry(entry, cancel: CancelToken, chunk_size=1<<20) -> None` copies one file in
  `chunk_size` chunks via manual `shutil.copyfileobj`-equivalent, checking `cancel` between
  chunks (raises `OperationCancelled` when set — caught by the caller, chunk boundary = the
  cancellation guarantee); directories are `os.makedirs`'d, not chunk-copied; symlinks use
  `os.symlink(os.readlink(src), dst)`, never followed; `shutil.copystat` after each file/dir
  completes. `execute_plan(plan, cancel, conflict_policy, on_progress: Callable[[OpProgress],
  None]) -> ExecutionResult` (frozen dataclass: `completed: tuple[PlanEntry, ...]`, `skipped:
  tuple[PlanEntry, ...]`, `cancelled: bool`) drives the per-entry loop, calling `conflict_policy`
  when `entry.dst` already exists, calling `on_progress` after each entry (speed/ETA computed from
  a monotonic clock and bytes-done-so-far — inject the clock for deterministic tests).
- No Textual worker/thread wiring yet — that's MC-027 (the first real UI consumer); this issue's
  `execute_plan` is a plain synchronous function a worker thread will call.

**Dependencies:** None

**Expected result:**
A complete, synchronous, cancelable copy/plan engine — metadata-preserving, symlink-safe,
conflict-policy-injectable — ready for a Textual worker to drive from MC-027 onward.

**Acceptance criteria:**
- [ ] `mycom/llm/` and `mycom/plugins/` no longer exist; full suite still green (nothing imported
      them).
- [ ] `build_plan` on a mixed tree (files, nested dirs, a symlink) produces the correct entry list,
      byte total, and file count (dirs excluded from `total_files`).
- [ ] `copy_entry` preserves mtime/permissions (`shutil.copystat`) and copies a symlink as a
      symlink (never dereferenced).
- [ ] `execute_plan` calls `on_progress` with monotonically non-decreasing `bytes_done`/
      `files_done`; cancelling mid-tree (via `CancelToken`) stops at the next chunk boundary,
      leaves already-copied files byte-identical and intact, and reports `cancelled=True`.
- [ ] A conflict on an existing `dst` calls the injected `conflict_policy` and honors
      `SKIP`/`OVERWRITE`/`RENAME`/`CANCEL` correctly (fake policy in tests, no dialog needed here).
- [ ] **Unit test:** plan builder (files/dirs/symlinks, byte/file counts), copy correctness
      (content + metadata, tmpfs fixtures), cancellation-mid-tree leaves source and
      already-copied-destination files intact, conflict-policy dispatch for every `ConflictChoice`.

### MC-026 — Conflict resolution dialog (F0.10)

**Description:**
Raised by copy/move/rename when a target already exists: shows both files' size/mtime (newer
marked), six choices. Built on `DialogKit` (v0.2); the `ConflictPolicy` callable MC-025's engine
calls.

**What needs to be done:**
- `mycom/widgets/dialog.py` (or a new `mycom/widgets/conflict_dialog.py` if `dialog.py` is getting
  large): `ConflictDialog(DialogKit[tuple[ConflictChoice, Path | None]])` — message body shows
  `new: {size} {mtime}` / `existing: {size} {mtime}` with the newer one flagged; six
  `DialogButton`s (`Overwrite`/o, `Skip`/s, `Rename`/r, `Overwrite All`/w, `Skip All`/k,
  `Cancel`/c — six distinct hotkeys, verified against MC-016/v0.2's duplicate-hotkey guard).
  `Rename` doesn't dismiss immediately — it swaps in an `Input` (reusing the `compose_body`
  extension point) pre-filled with the conflicting name for editing, with its own `OK`/`Cancel`
  pair, then dismisses with `(ConflictChoice.RENAME, new_path)`.
- A small adapter class implementing MC-025's `ConflictPolicy` protocol by `push_screen`-ing
  `ConflictDialog` and blocking the calling worker thread on the result (via a
  `threading.Event`/queue handoff, since the policy is called from a worker thread but the dialog
  must be shown on the main Textual thread — `App.call_from_thread` to show it, block on a
  `queue.Queue.get()` for the answer) — this is the seam where "All" persistence lives (the
  adapter remembers `OVERWRITE_ALL`/`SKIP_ALL` for the rest of one `execute_plan` call and stops
  asking).
- Directory-over-directory: merges (recurses into both, surfacing **per-file** conflicts
  individually rather than one dialog for the whole directory) — this is a `build_plan`/
  `execute_plan` behavior (a directory `PlanEntry` whose `dst` already exists as a directory is
  not itself a conflict; only its individual file entries are checked). File-over-directory and
  directory-over-file are refused outright (not offered through the six choices) with a clear
  `ErrorDialog` explanation.

**Dependencies:** MC-025

**Expected result:**
Every conflict during copy/move/rename gets a consistent, keyboard-driven resolution dialog;
"All" answers apply for the rest of that one operation only.

**Acceptance criteria:**
- [ ] Dialog shows both files' size/mtime with the newer one visually marked.
- [ ] All six choices produce the correct `(ConflictChoice, Path | None)` result; `Rename`'s
      follow-up input pre-fills the conflicting name.
- [ ] Dir-over-dir merges (per-file conflicts surface individually, not one dialog for the whole
      tree); file-over-dir and dir-over-file are refused with an explanation, never offered the
      six-choice dialog.
- [ ] "All" choices don't leak into a *subsequent, separate* operation — verified via two
      sequential `execute_plan` calls with fresh adapters.
- [ ] **Pilot test:** each of the six choices driven via keyboard (hotkey + Enter paths).

### MC-027 — Copy (F5)

**Description:**
`F5` copies selection-else-cursor (the v0.3 contract) to a target path pre-filled with the passive
panel's directory; recursive; progress dialog with per-file + total bars, bytes, speed, ETA;
`Esc` cancels at a chunk boundary; self-copy refused; passive panel refreshes on completion.

**What needs to be done:**
- `mycom/keymap.py`: `Command("copy", ("f5",), "panel", "Copy", slot=5)` already exists (v0.1) —
  wire `MyComApp.action_copy` (the slot was reserved, now gets its handler).
- `mycom/widgets/dialog.py`: `OperationProgressDialog(DialogKit[None])` — two `ProgressBar`s
  (per-file, total), labels for current file name, bytes copied/total, speed, ETA; a `Cancel`
  button that sets the `CancelToken` MC-025 defines (does not itself stop the worker — just
  signals it); no `Esc`-equals-dismiss shortcut bypassing Cancel (mirrors v0.2's deliberate
  `ProgressDialog.key_escape` no-op decision, now with a real Cancel button as the correct
  affordance instead).
- `MyComApp.action_copy`: `panel.get_selected_files()` (v0.3 contract) → refuse (via `ErrorDialog`)
  if the inactive panel's directory is a descendant of (or equal to) any source → `InputDialog`
  pre-filled with `self.inactive_panel.current_path` (title `Copy "{name}"` / `Copy {n} files`) →
  on confirm, `build_plan` → run `execute_plan` in a Textual thread worker
  (`self.run_worker(..., thread=True)`), the `ConflictDialog` adapter (MC-026) as the injected
  policy, `on_progress` marshalling `OpProgress` back to the main thread via `call_from_thread` to
  update `OperationProgressDialog` → on completion, dismiss the progress dialog,
  `self.inactive_panel.refresh_listing()` (and the active panel, since selection/cursor may need
  updating too), deselect the completed entries (v0.3's `deselect()` contract).
- Metadata/symlink correctness and cancellation semantics come from MC-025 — this issue is the
  wiring, not new copy logic.

**Dependencies:** MC-025, MC-026

**Expected result:**
`F5` copies a 1 GB tree byte-identical with preserved mtimes, live progress, a reachable cancel,
and a refreshed passive panel — exactly F0.6's acceptance bar.

**Acceptance criteria:**
- [ ] Copying a 1 GB tmpfs tree completes byte-identical with preserved mtimes; dialog totals
      match the plan's `total_bytes`/`total_files`.
- [ ] The UI stays responsive during a large copy (panel redraw/cancel reachable — verified by
      the worker running off the event loop).
- [ ] Copy onto itself or into its own subdirectory is refused with a clear error before any I/O.
- [ ] Cancel mid-copy leaves already-copied files intact and the source untouched.
- [ ] Passive panel shows the new files when the operation completes.
- [ ] **Integration test:** a scripted multi-conflict copy exercises all six `ConflictDialog`
      choices correctly (the F0.10 "10-conflict fixture" DoD item, satisfied here since Copy is
      the first real consumer).

### MC-028 — Move (F6): same-FS rename + cross-device copy-and-verified-delete

**Description:**
Same-filesystem move is an instant `rename()`; cross-device move reuses the copy engine, deleting
each source file only after its copy is verified complete. Shares the conflict dialog with copy.

**What needs to be done:**
- `mycom/keymap.py`: wire `MyComApp.action_move` to the existing `move` (`f6`) slot.
- `mycom/fileops/engine.py`: `same_filesystem(a: Path, b: Path) -> bool` (`os.stat().st_dev`
  comparison); `move_entry(entry, cancel) -> None` — `Path.rename()` when same-filesystem
  (no progress dialog, no chunking — instantaneous by definition), else `copy_entry` followed by
  verifying the destination's size/mtime match before `src.unlink()` (never delete first).
- `MyComApp.action_move`: mirrors `action_copy`'s flow (target dialog, plan, conflict policy,
  progress) but routes each entry through `move_entry`; when every entry in the plan is
  same-filesystem, skip the progress dialog entirely (instantaneous, per F0.6's "no progress
  dialog flicker" acceptance box) — only show it for a cross-device plan.

**Dependencies:** MC-027

**Expected result:**
`F6` on the same filesystem is instant with no dialog flicker; across filesystems it's a verified
copy-then-delete with the same progress/cancel/conflict UX as copy.

**Acceptance criteria:**
- [ ] Same-FS move of a large directory is instantaneous, no progress dialog shown.
- [ ] Cross-device move: source deleted only after its copy is verified; a cancelled cross-device
      move leaves the source fully intact and reports the partial target.
- [ ] Conflicts during move use the same `ConflictDialog` as copy.
- [ ] **Unit test:** `same_filesystem` detection (mocked `st_dev`); `move_entry`'s
      verify-before-delete ordering (a fault-injected "copy succeeds but verification fails" case
      must leave the source untouched).
- [ ] **Integration test:** cross-device move cancellation leaves source intact (tmpfs fixture
      simulating a second filesystem via a bind-mount-free `st_dev` monkeypatch, since a real
      second filesystem isn't available in CI).

- [ ] Invalid characters / permission errors are reported via `ErrorDialog`, never a crash.

### MC-030 — Delete (F8)

**Description:**
`F8` permanently deletes selection-else-cursor after confirmation (stronger for non-empty
directories); read-only files prompt individually; progress for large trees; cursor moves to the
next surviving entry.

**What needs to be done:**
- `mycom/keymap.py`: wire `MyComApp.action_delete` to the existing `delete` (`f8`) slot.
- `mycom/fileops/engine.py`: `delete_entry(entry, cancel) -> None` (`Path.unlink()` for files/
  symlinks, `Path.rmdir()` for already-emptied dirs — directories are walked and their contents
  deleted bottom-up by `execute_plan`'s delete mode, mirroring the copy-mode walk order in
  reverse).
- `MyComApp.action_delete`: `ConfirmDialog("Delete \"{name}\"?")` / `"Delete {n} files?"` (red
  accent title per F0.8's UI note — a `title_style`/CSS class on `DialogKit` if not already
  supported, else a plain red-colored title label); a **second**, stronger confirmation
  (`"Directory \"{name}\" is not empty. Delete anyway?"`) for any non-empty directory in the
  selection; a read-only file (no write permission) prompts
  `ConfirmDialog("Delete read-only file \"{name}\"?")` individually rather than failing silently.
  On confirm: `build_plan`-equivalent walk (reusing MC-025's walker in "delete mode" — no `dst`,
  just the entries to remove) → `execute_plan`-style loop calling `delete_entry`, progress dialog
  only for large trees (reuse `OperationProgressDialog` from MC-027, single-bar mode when there's
  no meaningful "total bytes" concept — total *files* instead). `Esc`/Cancel anywhere aborts with
  not-yet-processed files intact. On completion: refresh, cursor to the next surviving entry
  (`FileList.select_by_name` on whatever followed the deleted cursor row before the refresh,
  reusing the v0.1 cursor-restore pattern), deselect completed entries.

**Dependencies:** MC-025, MC-026

**Expected result:**
`F8` deletes permanently with the right confirmation ladder, never silently fails on a read-only
file, and leaves the cursor on a sensible next entry.

**Acceptance criteria:**
- [ ] Single file, multi-selection, and non-empty-directory deletes each get the right
      confirmation(s).
- [ ] Read-only files prompt individually instead of failing silently.
- [ ] `Esc`/Cancel anywhere aborts with not-yet-processed files intact.
- [ ] Cursor moves to the next surviving entry after deletion.
- [ ] **Integration test:** the full confirmation ladder (single/multi/non-empty-dir/read-only)
      and cancel-mid-delete, tmpfs fixtures with a real read-only-permission file (not mocked).

### MC-031 — Rename (Shift+F6)

**Description:**
`Shift+F6` renames the cursor entry in place: dialog pre-filled with the current name, stem
pre-selected. Renaming onto an existing name goes through the conflict dialog, not an exception.

**What needs to be done:**
- `mycom/keymap.py`: `Command("rename", ("shift+f6",), "panel", "Rename")` (new — F6 alone is
  `move`, `Shift+F6` is the separate in-place rename action per F0.9).
- `MyComApp.action_rename`: an `InputDialog` variant (or a small `RenameDialog(DialogKit)` if
  `InputDialog`'s plain `Input` can't pre-select a substring — check Textual `Input`'s selection
  API first, prefer extending `InputDialog` with an optional `select_stem: bool` over a whole new
  class if it can) pre-filled with the cursor entry's name, with the stem (name minus extension,
  matching FAR convention) pre-selected as if for immediate overtyping. On confirm with a
  different name: if the target doesn't exist, a direct same-directory `move_entry` (MC-028) —
  effectively free, since it's always same-filesystem; if it does exist, routes through
  `ConflictDialog` (MC-026) exactly like move, never raising `FileExistsError` to the user.
- After success: cursor follows the renamed entry to its new sort position (`select_by_name` on
  the new name after `refresh_listing()`).

**Dependencies:** MC-028

**Expected result:**
`Shift+F6` renames in place with the stem pre-selected for fast overtyping; a collision is a
normal conflict-dialog flow, not a crash; the cursor tracks the renamed entry.

**Acceptance criteria:**
- [ ] Dialog pre-fills the current name with the stem pre-selected.
- [ ] Renaming to an existing name opens `ConflictDialog`, never raises.
- [ ] Cursor follows the renamed entry to its new sort position.
- [ ] Works on directories, not just files.
- [ ] **Pilot test:** rename flow incl. the pre-selected-stem behavior and the conflict path.

in `spec/architecture.md` §File operations engine, so no doc change needed beyond what this phase
implements.

against real tmpfs fixtures (huge sparse files for the 1 GB cases, real read-only-permission
files, `st_dev` monkeypatching to simulate cross-device moves) — never mocked filesystem behavior,
per `spec/architecture.md` §Testing and CI.
