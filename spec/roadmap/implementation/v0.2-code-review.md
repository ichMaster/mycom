## Findings

### 1. 🟠 Arrow-key focus cycling dead-ends into the Input field

**File:** `mycom/widgets/dialog.py` (`DialogKit.on_key`)

**Failure scenario:** `on_key`'s arrow-handling branch calls `self.focus_previous()`/
`self.focus_next()` — Textual's generic focus-chain walk, which includes **every** focusable
widget in the dialog, not just buttons. On `InputDialog` (a real, shipped v0.2 dialog — used for
rename/mkdir-style prompts), pressing `Tab` then `Right` twice moves focus
Input→OK→Cancel→**Input**. Once focus lands back on the `Input`, `on_key`'s
`if not input_focused:` guard (correctly, per spec) stops handling arrows at all — but the
`Input` widget's own key handling consumes `Left`/`Right` for text-cursor movement and never
returns focus to a button. The user is stuck: only `Tab`/`Shift+Tab` can escape. This directly
contradicts the class's own docstring ("`Left`/`Up`/`Right`/`Down` additionally cycle focus
between buttons") and is a real keyboard-first violation (mission principle) — verified live; no
existing test exercises arrow navigation starting from a button on a dialog that also contains an
`Input`, which is exactly why it shipped uncaught.

**Fix:** cycle among `Button` widgets only (query `self.query(Button)`, not the generic focus
chain), so arrow navigation can never land on — or get stuck behind — an `Input`. `Tab`/
`Shift+Tab` keep using Textual's normal chain (including the `Input`), which is correct and
unchanged.

### 2. 🟡 No duplicate-hotkey guard

**File:** `mycom/widgets/dialog.py` (`DialogKit.__init__` / `on_key`)

**Failure scenario:** Nothing prevents two `DialogButton`s in the same `buttons` tuple from
declaring the same `hotkey` letter. `on_key`'s hotkey loop matches the **first** button with a
given letter, so the second's hotkey is silently and permanently unreachable — no error, no
warning. Doesn't affect any dialog shipped in v0.2 (Yes/No = y/n, OK/Cancel = o/c — all distinct),
but v0.4's conflict dialog (Overwrite/Skip/Rename/Overwrite All/Skip All/Cancel — six buttons) is
the very next multi-button dialog built on this kit, and six mnemonics is exactly where a
collision becomes an easy mistake to make and hard to notice.

**Fix:** a cheap assertion in `DialogKit.__init__` — collect the hotkey letters actually in use
and raise `ValueError` on a duplicate. Fails fast at dialog-construction time (caught immediately
in dev/tests) rather than silently swallowing a button forever.

### 3. 🟡 Theme-variable dependency has no graceful fallback (informational, no action)

**File:** `mycom/theme.py` and every widget's `DEFAULT_CSS` referencing `$panel-bg` etc.

Mounting any theme-variable-referencing widget under an `App` that never calls
`register_theme`/sets `self.theme` raises `UnresolvedVariableError` and crashes outright — no
graceful degradation. Verified this **does not** happen anywhere in the shipped app:
`MyComApp.__init__` registers and activates `far-classic` before `compose()` ever runs (correct
ordering, confirmed live), and `tests/support.py::ThemedApp` already exists for isolated-widget
test harnesses. Recorded for completeness since the question was explicitly asked — not a defect
in what v0.2 ships, and not being fixed or deferred; any future direct-construction entry point
(a debug script, a widget preview tool) that skips theme registration would need to know this, but
building a fallback theme for a scenario nothing currently exercises would be speculative
over-engineering.

## What's solid

- Theme registration ordering in `MyComApp.__init__` is correct — verified live: the app starts
  with `app.theme == "far-classic"` and zero CSS errors.
- `is_active` reflects `add_class`/`remove_class` immediately (a Python set operation, not a
  deferred CSS pass) — no stale-footer race; `activate()`/`deactivate()` correctly re-run
  `_update_footer()`, confirmed live and by `test_footer_updates_when_panel_activation_changes`.
- `_update_footer()` and `activate()` are safe even before mount (verified live, no crash) —
  `self._footer` is a real `Static` constructed in `__init__`.
- `ProgressDialog` (zero buttons): `key_enter` no-ops safely (verified live); the deliberate
  `key_escape` no-op does **not** block a programmatic `dismiss()` call — verified live, so v0.4's
  operation engine can still dismiss it when an operation completes.
- `Keymap.key_bar_slots`: `range(1, 11)` is correctly F1-F10, no off-by-one; no actual slot
  collision exists in `DEFAULT_COMMANDS` today.
- `StatusBar`'s async `on_click` is the only async message handler in the touched files; no other
  sync/async mismatches found. No single-writer violation — Textual's serial message pump means
  rapid double-clicks process one at a time, not concurrently.
- No leftover hard-coded hex colors outside `theme.py`; no ad-hoc `ModalScreen`/`push_screen` usage
  outside `dialog.py` — the "zero ad-hoc modal code" audit holds.
- Full suite: 156/156 passing at review time.
