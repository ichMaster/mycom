# v0.6 — GitHub Issues

Issues for phase **v0.6 — Viewer and editor** (version **v0 — MVP**), derived from the per-phase
Tasks in [roadmap.md](../../roadmap.md) (§v0.6) and the components in
[architecture.md](../../../spec/architecture.md) (Viewer and editor). This file is scoped to a
single phase; IDs continue from v0.5 (MC-035 → **MC-036…MC-040**).

Implements F0.12 (viewer) and F0.13 (editor). The viewer's contract is *instant at any size*
(windowed/mmap reads, never loading a file whole); the editor's contract is *trust* (dirty-close
guard, external-change guard, EOL and trailing-newline preservation, binary/oversize redirect to
the viewer). `$EDITOR` via `App.suspend()`/resume (the same mechanism v0.5's command execution
uses) is the permanent escape hatch and the scope guard against editor feature creep.

**Reconciliation note (ship-phase RECONCILE step):** `MyComApp._handle_enter`'s file branch is
still a documented no-op ("File open is handled by viewer/editor in later phases"). F0.12/F0.13
prescribe `F3`/`F4` as the entry points; neither spec's acceptance criteria mention `Enter`
opening the viewer. This phase wires `F3`/`F4` only — `Enter`-on-a-file stays a no-op, a deliberate
scope boundary, not a gap to close here.

## v0.6 — Viewer and editor

### MC-036 — Viewer engine: windowed/mmap reads, encoding fallback

**Description:**
The viewer's core contract — instant open and instant `End`-to-EOF at any file size, with RSS
staying bounded while paging through a huge file — is impossible with a naive "read the whole
file" approach. `mycom/viewer/buffer.py`: a pure, Textual-free engine (mirrors `fileops/`'s and
`console/`'s shape) built on a read-only `mmap.mmap`, indexing only the window currently in view
(and a small lookback margin), never the whole file.

**What needs to be done:**
- `mycom/viewer/buffer.py`: `ViewerBuffer(path: Path)` — opens the file and `mmap.mmap(fd, 0,
  access=ACCESS_READ)`; does **no eager scanning** of the whole file (no full line-offset index —
  for a multi-GB file with millions of lines, even a Python list of line-start ints would itself
  blow the RSS budget). Probes encoding once at open (a few KB from the start): try strict UTF-8
  decode, fall back to `errors="replace"` UTF-8, then latin-1 if the file looks binary-ish
  (contains embedded NUL bytes or a high proportion of non-printable bytes in the probe) — auto-
  detection beyond this MVP heuristic is out of scope (P1 per F0.12).
- `read_lines_forward(offset: int, count: int) -> tuple[list[str], int]`: scans forward from
  `offset` splitting on `\n` (bytes, via the mmap, not a Python-level full read), decodes each
  line with the probed encoding, returns the lines plus the file offset just past the last one
  returned (for chaining the next read). Never reads more than a small bounded chunk ahead of what
  `count` requires.
- `read_lines_backward(offset: int, count: int) -> tuple[list[str], int]`: same, scanning
  backward from `offset` — needed for `PageUp`/arrow-up and for `End`'s "show the last N lines"
  (seek near EOF, scan backward for `count` line boundaries, bounded by a max lookback so a
  file with one absurdly long "line" — e.g. minified JSON — doesn't scan unboundedly; cap and
  mark truncated rather than hang).
- `size` (file size in bytes, from `mmap`/`stat`, O(1)) and `eof_offset` properties.
- Context-manager support (`__enter__`/`__exit__` or explicit `close()`) — the `mmap` and file
  descriptor must be released when the viewer screen closes.

**Dependencies:** None

**Expected result:**
A file of any size opens and seeks to EOF in bounded time with bounded memory — the actual engine
a viewer screen (MC-037) renders from.

**Acceptance criteria:**
- [ ] Opening a multi-GB sparse file (tmpfs fixture) and reading a window completes in well under
      300 ms; reading near EOF (`read_lines_backward` from the end) is similarly fast.
- [ ] RSS growth while paging forward through a large file across many reads stays bounded (no
      unbounded accumulation — verified by checking process memory before/after many
      `read_lines_forward` calls, not just "it didn't crash").
- [ ] A valid UTF-8 file decodes correctly; a file with invalid UTF-8 bytes still returns lines
      (via `errors="replace"` or the latin-1 fallback), never raises.
- [ ] `read_lines_backward` on a file with one pathologically long line (no `\n` within the
      lookback cap) returns a bounded, marked-truncated result rather than scanning unboundedly.
- [ ] **Unit test:** forward/backward reads at start/middle/EOF, encoding fallback (valid UTF-8,
      invalid UTF-8, embedded NUL "binary-ish" content), the long-line lookback cap, bounded
      memory across repeated reads on a large real (tmpfs) fixture — no mocks, real files.

### MC-037 — Viewer screen: F3, navigation, wrap toggle, status bar, F6→editor

**Description:**
Wires `ViewerBuffer` into a real Textual screen: `F3` opens the cursor file read-only; arrows/
PgUp/PgDn/Home/`End` navigate; `F2` toggles wrap (preserving the top visible line's file
position); a status bar shows filename/size/offset/percent; `F6` switches to the editor at the
same position, closing the viewer; `F3`/`F10`/`Esc` close back to the panels.

**What needs to be done:**
- `mycom/viewer/screen.py`: `ViewerScreen(Screen)` (not modal — full-screen, like the panels
  themselves) — owns a `ViewerBuffer`, renders the current window of lines (a `Static`/`RichLog`-
  style body; wrapping on/off toggles the widget's own wrap setting, Textual's own line-wrap
  support if the underlying widget has it, else re-render logic that preserves the *file offset*
  of the top visible line across the toggle — not just the *line index*, since re-wrapping changes
  how many file-lines fit on screen).
- Keymap: a new `"viewer"` context (`Keymap`/`Command` already support arbitrary named contexts —
  no registry changes needed beyond adding entries) — `Command("view", ("f3",), "panel", "View",
  slot=3)` already exists as the *open* trigger from the panel; within the viewer itself, bind
  arrows/PgUp/PgDn/Home/End (navigation, not `App.bind` globally — scoped to `ViewerScreen`'s own
  key handling so panel bindings don't leak in), `F2` (wrap), `F6` (open in editor), `F3`/`F10`/
  `Esc` (close).
- `MyComApp.action_view`: `F3` on the active panel's cursor file (not a directory) pushes
  `ViewerScreen(path)`. On close, refresh nothing (the viewer is read-only, nothing to refresh).
- Status bar: filename, `format_size` (reuse `mycom.utils.fs.format_size`), current top-line file
  offset, and `offset / size * 100` percent.
- `F6` from the viewer: closes `ViewerScreen`, opens `EditorScreen` (MC-039) at the same top-line
  offset — implemented once MC-039 exists; until then, this issue can wire the *action* (dismiss +
  a callback the app resolves) without a working target, since MC-039 depends on this issue
  existing first, not the reverse — avoid a forward-reference deadlock by having `F6`'s handler
  live in `MyComApp` (which both screens report to), not screen-to-screen.

**Dependencies:** MC-036

**Expected result:**
`F3` opens any file instantly, read-only, with working navigation and an accurate status bar;
`F6` hands off to the editor at the same position.

**Acceptance criteria:**
- [ ] A multi-GB file opens via `F3` and reaches EOF via `End` in well under 300 ms (reusing
      MC-036's own timing guarantee through the real screen, not re-measuring from scratch).
- [ ] Wrap toggle (`F2`) preserves the top visible line's *file position* (not just its on-screen
      row), verified by checking the same file offset is visible immediately before and after
      toggling.
- [ ] A file modified externally while viewing doesn't crash the viewer (a stale window is
      explicitly acceptable per F0.12 — no live-reload requirement in v0).
- [ ] `F3`/`Esc`/`F10` all close the viewer back to the panels, unchanged.
- [ ] **Pilot test:** open via `F3`, navigate (arrows/PgUp/PgDn/Home/End), toggle wrap and confirm
      position preservation, close via each of the three close keys.

### MC-038 — Editor engine: EOL/trailing-newline/binary/size detection

**Description:**
The pure logic the editor screen (MC-039) needs to be trustworthy: detecting a file's line-ending
convention and trailing-newline state on open so both are preserved byte-for-byte on save
(anything else produces a spurious diff on every save, which is precisely the failure mode that
makes a built-in editor untrustworthy), plus the binary/oversize checks that redirect to the
viewer instead of attempting to edit something the editor can't safely round-trip.

**What needs to be done:**
- `mycom/editor/detect.py`: `EolStyle` enum (`LF`, `CRLF`, `MIXED_LF_DOMINANT`,
  `MIXED_CRLF_DOMINANT`) and `detect_eol(text: str) -> EolStyle` — counts `\r\n` vs. bare `\n`
  occurrences; if both are present, "dominant" is whichever is more frequent (ties break to `LF`,
  matching the more common convention); a file with no line endings at all (single line, or
  empty) defaults to `LF` (the save-time default, not a claim about what was "detected").
  `has_trailing_newline(text: str) -> bool`. `apply_eol(text: str, style: EolStyle) -> str` —
  converts internal `\n`-normalized text back to the target style for writing (Textual's
  `TextArea` works in `\n`-normalized text internally regardless of source EOL, so this is the
  save-time re-application step).
- `mycom/editor/detect.py`: `is_binary(sample: bytes) -> bool` — a pragmatic MVP heuristic
  (embedded NUL byte, or a high proportion of non-printable/non-UTF-8-continuation bytes in a
  probe of the first ~8 KB) consistent with `spec/architecture.md`'s "binary... redirect to the
  viewer" contract; `MAX_EDITABLE_SIZE = 10 * 1024 * 1024` (10 MB) and a `too_large(path) -> bool`
  helper.
- Reading: `read_text(path) -> tuple[str, EolStyle, bool]` (text normalized to `\n`, detected EOL
  style, trailing-newline flag) — UTF-8 only, raises a specific `NotEditableError` (with a reason:
  binary vs. too-large) for the editor screen to catch and redirect rather than silently
  mis-decoding.

**Dependencies:** None

**Expected result:**
Opening any editable text file captures exactly what's needed to write it back byte-identical
except for the user's own edits; a binary or oversize file is identified before the editor ever
tries to load it.

**Acceptance criteria:**
- [ ] A pure-LF file, a pure-CRLF file, and a mixed file (majority LF with a few stray CRLF, and
      vice versa) each detect the correct `EolStyle`.
- [ ] A file with no trailing newline round-trips through `apply_eol` without gaining one; a file
      that has one keeps it.
- [ ] A binary fixture (embedded NUL bytes) and a valid UTF-8 text file are correctly
      distinguished by `is_binary`.
- [ ] A file just over 10 MB is flagged by `too_large`; one just under is not.
- [ ] `read_text` raises `NotEditableError` (not a generic exception, not a silent wrong-encoding
      read) for both the binary and oversize cases, with the reason distinguishable.
- [ ] **Unit test:** EOL detection (LF/CRLF/both mixed-dominant directions/empty/single-line),
      trailing-newline round-trip, binary detection (real binary fixture, not simulated), the
      10 MB boundary (just under / just over), `NotEditableError` reason for each redirect case.

### MC-039 — Editor screen: F4, TextArea, save/save-as, dirty-close guard

**Description:**
`F4` opens the cursor file in a Textual `TextArea`-based editor: undo/redo, `F2` save, `Shift+F2`
save-as, a modified-guard (Save/Discard/Cancel) on close, EOL/trailing-newline preserved on save,
and a binary/oversize file redirected to the viewer (MC-037) with a notice instead of attempted.

**What needs to be done:**
- `mycom/editor/screen.py`: `EditorScreen(Screen)` — `compose_body` yields a Textual `TextArea`
  loaded via MC-038's `read_text` (catch `NotEditableError`, show a brief notice, push
  `ViewerScreen` instead and return — the redirect F0.13 requires). Tracks `modified` via
  `TextArea.changed`-equivalent (Textual's `TextArea` posts a `Changed` message on every edit;
  compare against a `_saved_text` snapshot rather than trusting a single boolean flag, so
  undo-back-to-saved-state correctly clears the modified flag too, not just "any edit happened").
- `F2` (save): writes `apply_eol(text_area.text, self._eol_style)` (+ trailing newline per the
  detected flag) back to the file; updates `_saved_text`; runs the external-change check (MC-040)
  first.
- `Shift+F2` (save-as): `InputDialog` for a new path, then the same write logic at the new
  location; the editor continues editing the *new* path afterward (matches FAR's own save-as
  semantics — you keep working on what you just saved as).
- `Esc`/`F10` (close): if `modified`, `ConfirmDialog`-shaped three-way choice (Save/Discard/
  Cancel — `DialogKit` supports arbitrary button sets, this isn't a plain yes/no `ConfirmDialog`,
  so a small dedicated `DialogKit` subclass with three buttons); Cancel returns to editing,
  Discard closes without writing, Save writes then closes. Not modified: closes immediately.
- Status bar: filename, a `*` modified indicator, `line:col` (from `TextArea.cursor_location`),
  and the EOL style label.
- `MyComApp.action_edit`: `F4` on the active panel's cursor file (not a directory) pushes
  `EditorScreen(path)`; on close (any path — saved, discarded, or redirected to the viewer),
  refresh the active panel's listing (a save can change the file's size/mtime the panel shows).
- Wire MC-037's `F6`-from-viewer hand-off now that this screen exists: `MyComApp` closes
  `ViewerScreen` and opens `EditorScreen` at the same file, top-of-file (matching F0.12's "`F6`
  opens the same file in the editor at top of file" acceptance box — not the viewer's scroll
  position, deliberately, per the spec's own wording).

**Dependencies:** MC-038, MC-037

**Expected result:**
`F4` provides a trustworthy, undo-capable editor: a CRLF file saved without content changes
produces zero diff, quitting dirty always prompts, and nothing the editor can't safely round-trip
(binary, >10 MB) is ever attempted — it's redirected instead.

**Acceptance criteria:**
- [ ] Open→edit→save on a CRLF fixture keeps CRLF endings and produces no diff beyond the actual
      edit (byte-for-byte comparison outside the changed region).
- [ ] A trailing-newline-absent file stays absent after a no-content-change save; a
      trailing-newline-present file stays present.
- [ ] An undo/redo chain of 50+ operations replays correctly (`TextArea`'s own undo stack,
      exercised through real keypresses, not just calling an internal method).
- [ ] Quitting with unsaved changes always prompts; Cancel returns to editing with the buffer
      intact; Discard closes without writing; Save writes then closes.
- [ ] A binary file and a >10 MB file both redirect to the viewer with a notice instead of being
      loaded into the `TextArea`.
- [ ] **Pilot test:** open→edit→save round-trip (CRLF fixture), the three-way close-guard (all
      three choices), save-as continuing to edit the new path, binary/oversize redirect.

### MC-040 — External-change guard + `$EDITOR` escape hatch + key bar contexts

**Description:**
Closes out F0.13: a file touched on disk since the editor opened it warns before an overwriting
save (never a silent last-writer-wins); `Alt+F4` (and a config flag making `F4` do this by
default) hands editing to `$EDITOR` via the same suspend/resume mechanism v0.5's command execution
already uses; the viewer and editor each get their own key-bar context so labels never show panel
actions while either is open.

**What needs to be done:**
- `EditorScreen` records `path.stat().st_mtime` at open. Before the `F2` save-write, re-stat: if
  the mtime differs from what was recorded, show a `ConfirmDialog`-shaped warning ("File changed
  on disk since you opened it. Overwrite anyway?") before proceeding; declining returns to editing
  without writing (the in-memory buffer is never lost either way — this is a *warning*, not silent
  data loss in either direction).
- `mycom/config.py`: new `EditorConfig` dataclass (`external_default: bool = False`) wired into
  `AppConfig`/`load_config` exactly like the existing `GeneralConfig`/`LLMConfig` sections.
- `Command("edit_external", ("alt+f4",), "panel", "ExtEdit")` — `MyComApp.action_edit_external`:
  `with self.suspend(): subprocess.run([os.environ.get("EDITOR", "vi"), str(path)])` (no PTY-tee/
  ring-buffer machinery needed here — this is a simple "hand over the terminal, wait for exit,
  resume" case, unlike v0.5's command execution which needs to *capture* output; reuses
  `App.suspend()`, not `mycom.console.pty_runner.run_in_pty`) — then refresh the active panel
  (mtime/size may have changed). `MyComApp.action_edit`: if `self._config.editor.external_default`
  is set, call `action_edit_external` instead of pushing `EditorScreen`.
- Key bar contexts: `Command` entries for viewer/editor actions already carry `context="viewer"`/
  `"editor"` (MC-037/039) — confirm `StatusBar` is constructed per-screen (or re-configured on
  screen push/pop) with the right context so `F1 Help … F10 Quit`-style labels for panels never
  bleed into the viewer/editor key bar, and vice versa.

**Dependencies:** MC-039

**Expected result:**
Saving over an externally-modified file always warns first; `$EDITOR` is a real, working escape
hatch reachable both explicitly (`Alt+F4`) and as `F4`'s default behavior via config; the key bar
never shows the wrong context's labels.

**Acceptance criteria:**
- [ ] Modifying a file on disk (from outside the editor) after opening it, then saving, shows the
      external-change warning; declining preserves both the on-disk external change and the
      in-memory edit buffer; accepting overwrites as normal.
- [ ] `Alt+F4` suspends, runs `$EDITOR` on the cursor file, resumes, and refreshes the panel.
- [ ] `editor.external_default = true` makes plain `F4` behave like `Alt+F4`.
- [ ] The key bar shows viewer labels while the viewer is open and editor labels while the editor
      is open — never panel labels bleeding through, and never the reverse after closing back to
      panels.
- [ ] **Integration test:** external-change guard fires and both decline/accept paths preserve
      the correct state; `$EDITOR` round-trip (faked binary, not a real interactive editor, per
      the same "no paid/networked/real-external-program call in CI" discipline used for the
      `claude` binary elsewhere) refreshes the panel afterward.

## v0.6 scope notes

**Total effort:** ~4 weeks (2 L + 1 M + 1 L + 1 M).
**Critical path:** `MC-036`/`MC-038` (parallelizable) → `MC-037` → `MC-039` → `MC-040`.
**Phase DoD (roadmap §v0.6):** a 1 GB log opens in <300 ms with bounded RSS; a CRLF round-trip
produces no spurious diff; quitting dirty always prompts; `$EDITOR` round-trip works in tmux.
**Contracts pinned this phase:** `mycom/viewer/buffer.py` (`ViewerBuffer`) and
`mycom/editor/detect.py` (`EolStyle`, `detect_eol`, `is_binary`, `NotEditableError`) are new, pure,
Textual-free seams — mirroring `fileops/`'s and `console/`'s shape, already anticipated in
`spec/architecture.md` §Viewer and editor. A new `"viewer"`/`"editor"` keymap context is additive
to the existing `Keymap`/`Command` registry (no changes to its shape, just new entries) — no doc
change needed beyond what this phase implements. `EditorConfig` extends `AppConfig` the same way
`GeneralConfig`/`LLMConfig` already do.
**Mock note:** no paid APIs or `claude` binary this phase. `$EDITOR` in tests is a faked/trivial
binary (mirrors how the `claude` binary is faked elsewhere), never a real interactive editor
launched in CI. Viewer/editor tests run against real (tmpfs) fixtures — huge sparse files, real
CRLF/mixed-EOL/binary fixtures — never mocked file content, per `spec/architecture.md` §Testing
and CI.
