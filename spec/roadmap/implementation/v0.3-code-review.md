## Findings

### 1. 🟠 Any transient DB error is treated as corruption and wipes valid state

**File:** `mycom/state.py` (`StateDB._open`)

**Failure scenario:** `_open()`'s `try` wraps both the intended corruption probe (`SELECT count(*)
FROM sqlite_master`) **and** the entire `_migrate(conn)` call, under one
`except sqlite3.DatabaseError`. `sqlite3.OperationalError` (e.g. `"database is locked"`) is a
`DatabaseError` subclass, so a transient lock or I/O hiccup — not actual corruption — takes the
exact same path as real corruption: `self._path.unlink(missing_ok=True)` + silent recreate,
discarding all previously-saved state. Live-reproduced: injecting a single
`OperationalError("database is locked")` into `_migrate` on an otherwise valid, pre-populated DB
caused the file to be deleted and recreated empty; `get_panel_state("left")` returned `None`
afterward. No `PRAGMA busy_timeout` is set anywhere either, which makes `SQLITE_BUSY` more likely
the moment anything else touches the same `state.db` concurrently (a second `mycom` instance, or a
future v1.4 history writer). Broader than the documented intent
(`spec/architecture.md` §Persistence: "corrupt/missing DB recreates silently") — that should not
extend to transient, non-corruption errors.

**Fix:** narrow the corruption probe to its own `try`/`except`, separate from `_migrate()`; a
migration failure after a DB is confirmed to be valid SQLite is a different failure class and
should propagate (caught by `MyComApp.__init__`'s existing `StateDB()` try/except, which already
degrades to persistence-disabled-this-session rather than destroying data). Also set
`PRAGMA busy_timeout` on every connection to reduce spurious lock errors in the first place.

### 2. 🟠 Selection survives an external same-name file replacement (DEFERRED)

**Files:** `mycom/panels/file_browser.py` (`_selected`, `refresh_listing`, `set_show_hidden`),
`mycom/widgets/file_list.py` (highlight rendering)

**Failure scenario:** `_selected: set[str]` is cleared only in `navigate_to()`; `refresh_listing()`
/ `set_show_hidden()` / `set_sort()` all preserve it by design (roadmap: "survives sort/view
changes"). Live-reproduced: select `foo.txt`, then — without navigating away — an external process
deletes it and writes a brand-new, unrelated `foo.txt`; `Ctrl+H` (an ordinary v0.3 flow) triggers
`refresh_listing()`, and the new file renders yellow-highlighted with the footer showing
`"1 selected ({new file's size})"`, with no user action re-selecting it.

**Why deferred:** the underlying cause is that v0.3 has no filesystem-watching at all — a user can
only even observe this by triggering a manual refresh path (sort/hidden-toggle/view change), since
nothing auto-refreshes on external changes yet. **v1.2 owns exactly this territory**
(`spec/roadmap.md` §v1.2: "Auto-refresh: watchdog observers on both panel dirs... cursor **and
selection** preserved across refreshes") — that phase is where "what does the selection mean when
the directory changed out from under us" gets a real, designed answer (likely: identify entries by
more than bare name, or invalidate stale selections on a detected external change). Solving it here
piecemeal, without the watcher infrastructure that motivates the fix, risks a half-answer that v1.2
has to redo. Tracked for v1.2 planning to address.

### 3. 🟡 Unguarded final flush at quit can crash instead of a graceful exit

**File:** `mycom/app.py` (`action_quit`, `_flush_state`)

**Failure scenario:** `action_quit()` calls `self._flush_state()` synchronously and unwrapped;
`_flush_state()`'s `save_panel_state`/`save_app_state` calls are likewise unguarded. If the final
write raises (a second `mycom` instance holding the DB, a full disk, a read-only filesystem), the
exception propagates out of the action handler into Textual's panic/traceback screen instead of a
clean quit — inconsistent with `__init__`'s handling of the exact same failure class
(`StateDB()` construction is already wrapped, degrading gracefully to `self._state_db = None`).

**Fix:** wrap `_flush_state()`'s body in try/except, logging a warning on failure rather than
propagating — quitting the app must not depend on a successful final write succeeding.

### 4. 🟡 `set_show_hidden` flag can desync from the display on a failed refresh (DEFERRED)

**File:** `mycom/panels/file_browser.py` (`set_show_hidden`)

**Failure scenario:** `self._show_hidden = value` is set unconditionally before `refresh_listing()`
runs; if that call hits an `OSError` (permission revoked or the directory vanishes mid-toggle), the
flag no longer matches what's actually on screen, which can make the very next same-key toggle
behave as a no-op or re-trigger unexpectedly.

**Why deferred:** narrow trigger (permissions/vanishing mid-keypress), self-correcting on the
following toggle attempt, and severity is LOW. Parking as opportunistic polish rather than
pulling focus from the two real correctness/robustness fixes above.

## What's solid

- **Timer/quit ordering:** `action_quit` calls `Timer.stop()` (a synchronous cancel) before the
  final `_flush_state()`; single-threaded asyncio makes this race-free — confirmed via `Timer.stop()`
  semantics, no reproduction needed.
- **Single-writer rule:** no thread/worker/`asyncio.to_thread` anywhere in `state.py`/`app.py`; every
  SQLite call is synchronous, invoked only from Textual callbacks on the event loop.
- **Mask-dialog closure and the on_key screen-stack guard:** live-tested pressing `Ctrl+U` (bound
  app-wide to `panel_swap`, *not* in `_INTERCEPTED_ACTIONS`) and `Tab` while the mask `InputDialog`
  was open — neither reached app-level actions (`Input`'s own bindings and the modal's focus
  handling both absorb them). The `panel` reference captured in `_open_mask_dialog`'s closure
  cannot desync from a mid-dialog `Tab` switch, because `Tab` itself can't reach `action_switch_panel`
  while the dialog is open. Only two `push_screen` call sites exist app-wide, never nested, so the
  screen-stack guard has no legitimate multi-screen flow to break.
- **Last-row selection toggle:** `DataTable.cursor_coordinate` clamps rather than wrapping; toggling
  the last row selects it and the cursor correctly stays put — live-verified.
- **No hard-coded hex colors** in any changed file (`SELECTED_FG` sourced from `theme.py`); no
  `fileops/` code landed — confirmed no v0.4 (file operations) scope creep.

## Fixes applied

### 1. Transient DB errors no longer treated as corruption — ✅ FIXED — `0abbdc8`
**Change:** `StateDB._open()`'s corruption probe is now narrowly scoped to opening + validating the
file (`_connect()`'s `PRAGMA` calls, which is where a garbage/non-SQLite file actually fails, plus
the `SELECT` sanity check) — `_migrate()` runs **outside** that `try`/`except`, so a real
migration-time failure propagates as a normal exception instead of triggering a silent wipe. Added
`PRAGMA busy_timeout=5000` on every connection to reduce spurious `SQLITE_BUSY` errors in the
first place.
**Regression test:** `tests/unit/test_state.py::test_transient_operational_error_during_migrate_does_not_wipe_valid_data`
(injects a one-shot `OperationalError` into `_migrate` on a DB pre-populated with real state,
asserts the exception propagates *and* the file — and its data — survive intact on a normal
re-open) and `::test_busy_timeout_pragma_is_set`.
**Verification:** `pytest` 220 passed, `ruff check` clean.
**Architecture impact:** none — `spec/architecture.md` §Persistence's "corrupt/missing DB
recreates silently" contract is unchanged; this fix makes the implementation actually match that
contract's scope (corruption only) rather than over-applying it to transient errors.

### 3. Quit no longer crashes on a failed final save — ✅ FIXED — `bb024a6`
**Change:** `_flush_state()`'s body (the `save_panel_state`/`save_app_state` calls) now runs inside
a `try`/`except Exception`, logging a warning on failure instead of propagating — matching the
graceful-degradation posture `MyComApp.__init__` already applies when `StateDB()` construction
itself fails.
**Regression test:** `tests/integration/test_persistence.py::test_quit_does_not_crash_when_the_final_save_fails`
(monkeypatches `save_panel_state` to raise `OSError`, asserts `action_quit()` completes and
`app._exit` is set rather than the exception propagating).
**Verification:** `pytest` 221 passed, `ruff check` clean.
**Architecture impact:** none — internal robustness fix, no seam or documented contract changed.
