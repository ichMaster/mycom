## Findings

### 1. 🟡 LOW — Flaky cancellation test timing margin (pre-existing, surfaced during v0.5 work)

**Failure scenario:** `tests/integration/test_copy_keys.py::test_f5_cancel_button_mid_copy_leaves_source_intact`
(authored in MC-027, v0.4) injects a 30 ms delay per file via a monkeypatched `execute_plan`, then
waits 100 ms before clicking Cancel, expecting only a few of 20 files to have completed. The real
culprit isn't "more happens in the same 100ms" — `pilot.click()`'s own async dispatch can itself
be slow under system load (competing for the same event loop), while the background worker thread
keeps progressing independently the whole time regardless; a slow-enough click gives the worker
enough real wall-clock time to finish all 20 files (20 × 30ms = 600ms) before the cancel signal
actually lands. Not a v0.5 defect and not a data-loss risk — a test-timing-margin issue discovered
while running the full suite repeatedly during this phase's work, worth hardening now that it's
been observed rather than leaving it to flake again in CI.

**Proposed fix:** Widen the margin — either raise the per-file injected delay or lower the file
count-vs-wait-time ratio, so the "at least several files remain unprocessed" assertion holds
comfortably even under load.

### 2. 🟡 LOW — Console output recall isn't windowed for very large output

**Failure scenario:** A command that fills the ring buffer to its 100k-line cap, followed by
`Ctrl+O`: `_ConsoleOutputScreen` builds one `Static` from `RingBuffer.text()` (a single ~100k-line
string) inside a `VerticalScroll`. Textual's `Static` isn't virtualized — rendering/scrolling
through the full text could be noticeably slower than a windowed view, though it won't hang or
crash (confirmed no timeout in manual smoke-testing of the same code path via MC-033's 150k-line
`run_in_pty` test, which exercises the buffer-building side of this, just not the rendering side).

This isn't a new problem MyCom invented — it's the same "don't load huge content into a
non-windowed view" concern `spec/architecture.md` §Viewer and editor already names as the reason
the v0.6 viewer does windowed reads instead of loading a file whole. Console-output recall is a
much smaller, secondary surface than the viewer, and pulling windowed-rendering machinery forward
from v0.6 into v0.5 for this one recall screen would be scope creep for a "recall the last
output" feature whose acceptance criterion is just "Ctrl+O recalls the last console output," not
performance at the 100k-line ceiling.

**Proposed fix (deferred):** If real usage shows this is actually slow, reuse whatever windowed-
display primitive v0.6's viewer builds, rather than inventing a second one now.

## What's solid

- `run_in_pty`'s shell-command wrapping is exactly right for what it's for: `command` is the
  user's own typed shell input, meant to run as shell syntax (same trust boundary as typing
  directly into a terminal) — only `cwd` needs (and gets) `shlex.quote`.
- `RingBuffer` correctly separates "had output" from "what's still retained after eviction" —
  the F0.11 "skip Press any key when silent" behavior stays correct regardless of buffer size.
- The suspend/execute flow correctly treats the whole `with self.suspend(): run_in_pty(...)` block
  as an intentional, single-writer-safe blocking window: Textual isn't processing any UI messages
  while the terminal is genuinely the child's, so blocking the main thread for the command's whole
  duration is correct, not a violation.
- A vanished/EACCES active-panel directory at command-execution time is handled for free by the
  existing mechanism: the wrapped shell's own `cd` failure surfaces through the ordinary non-zero-
  exit-code path (`Exit code: N` + whatever the shell printed), no special-casing needed.
- `_MessageScreen`/`_ConsoleOutputScreen` are correctly *not* built on `DialogKit` (no title/
  button-row shape to reuse) and, having only one class in their own MRO defining `on_key`, aren't
  exposed to the MRO multi-dispatch hazard the v0.4 review found in `ConflictDialog`.
- Two real, load-bearing bugs (the `exec`-breaks-shell-syntax wrapping, and the deadlock from
  awaiting a Future a later keypress had to resolve) were caught and root-caused with live
  reproductions during MC-033/034's own implementation, not left for this pass to find.

## Fixes applied

### #1 — flaky cancellation test timing margin

**Commit:** 7275918

**Change:** `test_f5_cancel_button_mid_copy_leaves_source_intact`
(`tests/integration/test_copy_keys.py`) raised the per-file injected delay from 30 ms to 50 ms and
the pre-cancel wait from 0.1 s to 0.2 s, pushing the worst-case "all 20 files done" threshold
(1000 ms) well past the test's own deliberate wait (200 ms) — a much wider buffer against a slow
`pilot.click()` dispatch under system load.

**Regression test:** This *is* the regression-test fix — no new test needed; the existing test
already asserts the property (`len(copied) < 20`), it just needed a wider timing margin to assert
it reliably. Verified with 5 consecutive clean runs after the change (previously flaked once
across many runs).

**Verification:** `pytest` — 349 passed. `ruff check` — clean.

**Architecture impact:** None — a test-only timing constant change, no seam or contract touched.
