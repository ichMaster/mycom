# v0.2 — GitHub Issues

Issues for phase **v0.2 — Dialog kit, Far theme, key bar** (version **v0 — MVP**), derived from
the per-phase Tasks in [roadmap.md](../../roadmap.md) (§v0.2) and the components in
[architecture.md](../../../spec/architecture.md) (Dialog kit, Theme). This file is scoped to a
single phase; IDs continue from v0.1 (MC-013 → **MC-014…MC-018**).

v0.1 shipped three ad-hoc `ModalScreen` dialogs (`ConfirmDialog`, `InputDialog`, `ProgressDialog`,
plus `ErrorDialog` added mid-phase for EACCES) that each hand-roll their own frame/button/focus
code, and hard-code the FAR palette's hex values independently in five different widget files
(confirmed identical values everywhere — the palette itself is already right, per
[architecture.md](../../../spec/architecture.md)'s palette table). This phase extracts one dialog
engine and one theme file so nothing drifts, and adds the key bar the keymap registry was built to
drive.

## v0.2 — Dialog kit, Far theme, key bar

### MC-014 — Theme: single source of color + 256-color degradation check

**Description:**
The FAR classic palette is already correct (matches
[architecture.md](../../../spec/architecture.md)'s palette table exactly) but is hard-coded
independently in `app.tcss`, `panels/file_browser.py`, `widgets/file_list.py`,
`widgets/dialog.py`, `widgets/header.py`, `widgets/status_bar.py`, and `widgets/path_bar.py` — six
places any future palette change would have to touch. Move it into one theme file as Textual CSS
variables.

**What needs to be done:**
- `mycom/theme.py`: a Textual `Theme("far-classic", ...)` with named `variables` for every FAR
  role already in use — `panel-bg`, `panel-fg`, `panel-border`, `pathbar-active-bg/fg`,
  `pathbar-inactive-bg/fg`, `header-fg` (column headers), `cursor-bg/fg`, `selected-fg` (not yet
  consumed — no selection model until v0.3, but pinned now so it's not forgotten),
  `keybar-number-bg/fg`, `keybar-label-bg/fg`, `dialog-bg/fg`, `dialog-input-bg/fg` — values taken
  verbatim from the existing hard-coded hex (no palette change, just relocation); top-level
  `primary`/`background`/`surface` set from the same values for Textual's own chrome.
- `MyComApp.__init__` (before `compose`): `self.register_theme(FAR_CLASSIC_THEME)` and
  `self.theme = "far-classic"`.
- Replace every hard-coded hex literal in `app.tcss`, `panels/file_browser.py`,
  `widgets/file_list.py`, `widgets/dialog.py`, `widgets/header.py`, `widgets/status_bar.py`,
  `widgets/path_bar.py` with the matching `$variable` reference. Audit: `grep -rn
  '#[0-9a-fA-F]\{6\}' mycom/` returns nothing outside `mycom/theme.py` itself.
- 256-color degradation: MyCom relies on Textual's built-in automatic color downgrade (truecolor →
  256 → 16 → monochrome, based on detected terminal capability) rather than hand-rolling a
  redundant fallback table — document this decision in `theme.py`'s docstring. Add a unit test
  that downgrades every themed fg/bg role pair through Textual's `ColorSystem`/`Color` API to the
  `"standard"` (256-color) depth and asserts each pair stays visually distinct (no role collapses
  fg==bg).

**Dependencies:** None

**Expected result:**
One file is the single source of color; the app renders identically to v0.1 (same hex values, just
relocated), and a test pins that the palette survives 256-color degradation without collisions.

**Acceptance criteria:**
- [ ] `mycom/theme.py` defines every color role currently in use, with the same hex values as
      before (pure relocation, no visual change).
- [ ] `grep -rn '#[0-9a-fA-F]\{6\}' mycom/` matches nothing outside `mycom/theme.py`.
- [ ] App still renders correctly (existing Pilot tests pass unmodified — no widget-visible
      behavior change, only where the color values come from).
- [ ] **Unit test:** every themed fg/bg role pair remains distinct after downgrading to the
      256-color (`"standard"`) `ColorSystem` depth.

### MC-015 — Dialog kit engine

**Description:**
One reusable modal engine — framed window, title, message, extra body widgets, a button row —
that every dialog in the app builds on (F0.15). `Tab`/`Shift+Tab` cycle focus (free from Textual's
default focus chain); arrow keys additionally cycle focus between buttons (not while an `Input` has
focus, where arrows must move the text cursor instead); a labeled hotkey letter (bare letter, or
`Alt+letter` which always works even while an `Input` has focus) activates a button; `Enter`
activates the default button; `Esc` dismisses with a caller-supplied cancel result. Dialogs stack
(a dialog can `push_screen` another on top — Textual's `ModalScreen` stacking already provides
this; the kit doesn't fight it).

**What needs to be done:**
- `mycom/widgets/dialog.py`: a `DialogButton` frozen dataclass (`label`, `id`, `hotkey: str | None
  = None`, `default: bool = False`, `variant: str = "default"`) and a `DialogKit(ModalScreen)` base
  class:
  - `__init__(self, *, title="", message="", buttons=(), cancel_result=None, **kwargs)`.
  - `compose()`: title `Label` (if given), message `Label` (if given), `compose_body()` (override
    point for subclass-specific widgets, e.g. an `Input`), then a button row built from `buttons`
    — each label rendered with its hotkey letter wrapped in `[underline]…[/underline]` markup
    (Textual `Button` labels already interpret this).
  - `on_key`: when focus isn't on an `Input`, `left`/`up` → `focus_previous()`, `right`/`down` →
    `focus_next()`; hotkey matching (`key == f"alt+{letter}"` always, or bare `key == letter` only
    when an `Input` isn't focused) dispatches to the matching button's handling.
  - `key_enter`: activate the `default=True` button (or the last button if none marked default).
  - `key_escape`: `self.dismiss(cancel_result)`.
  - `on_button_pressed`: subclasses override `_result_for(button_id)` to map a pressed/activated
    button id to the dismiss value.
  - All CSS in `DialogKit.DEFAULT_CSS` references theme variables from MC-014 (`$dialog-bg`,
    `$dialog-fg`, `$dialog-input-bg`, `$dialog-input-fg`) — zero literal hex.
- Unit-testable in isolation (no dependency on the panel/app code) with a minimal harness screen.

**Dependencies:** MC-014

**Expected result:**
`DialogKit` is a complete, reusable base with no dialog-specific logic in it — every existing
dialog becomes a thin subclass (done in MC-016).

**Acceptance criteria:**
- [ ] A `DialogKit` with two buttons (one `default=True`) opened in a test app: `Tab`/`Shift+Tab`
      and `Left`/`Right` both cycle focus between the buttons.
- [ ] A labeled hotkey (e.g. `hotkey="y"` on a "Yes" button) activates that button on bare `y`
      when no `Input` is focused, and on `Alt+y` even when one is.
- [ ] `Enter` anywhere in the dialog activates the default button; `Esc` dismisses with
      `cancel_result`.
- [ ] Pushing a second `DialogKit` from within one already open stacks correctly (both mounted;
      dismissing the top one returns focus to the one below) — Textual's native `ModalScreen`
      stacking, exercised through the kit.
- [ ] **Pilot test:** hotkey activation, arrow/Tab focus cycling, Enter/Esc, and a stacked-dialog
      flow, all driven via `Pilot.press`.

### MC-016 — Rebuild Confirm/Input/Progress/Error dialogs on the kit

**Description:**
Rebuild all four v0.1 ad-hoc dialogs as thin `DialogKit` subclasses; delete the ad-hoc
frame/button/focus code each currently hand-rolls. Audit: zero ad-hoc modal code remains.

**What needs to be done:**
- `ConfirmDialog(DialogKit[bool])`: `buttons=(DialogButton("Yes", "yes", hotkey="y",
  default=True, variant="primary"), DialogButton("No", "no", hotkey="n"))`; `_result_for` maps
  `"yes"`/`"no"` → `True`/`False`; `cancel_result=False`.
- `InputDialog(DialogKit[str | None])`: `compose_body()` yields the `Input(value=default,
  id="input")`; buttons `OK`/`Cancel` (`OK` hotkey `o`, default); `_result_for("ok")` reads the
  `Input`'s current value, `_result_for("cancel")` → `None`; `cancel_result=None`. `Enter` while
  typing now correctly submits (the v0.1 gap where `InputDialog` had no `key_enter` at all is
  closed as a side effect of building on the kit).
- `ErrorDialog(DialogKit[None])`: single `OK` button (hotkey `o`, default); `cancel_result=None`.
- `ProgressDialog(DialogKit[None])`: `compose_body()` yields the `ProgressBar`; no buttons (kept
  as `ModalScreen`-level `update_progress()` — a progress dialog with a Cancel button belongs to
  the operation engine in v0.4, not invented here).
- Update the one existing consumer (`FileBrowserPanel._show_error`, v0.1) to the new `ErrorDialog`
  signature if it changed (it shouldn't — same `message` constructor arg).
- Delete every now-dead ad-hoc CSS block and focus-handling method the four dialogs used to define
  themselves.

**Dependencies:** MC-015

**Expected result:**
All four v0.1 dialogs behave identically from the outside (same construction signature, same
dismiss values) but share one engine; `grep` finds no second `ModalScreen` subclass defining its
own frame/button CSS.

**Acceptance criteria:**
- [ ] `ConfirmDialog`, `InputDialog`, `ErrorDialog`, `ProgressDialog` are all `DialogKit`
      subclasses; none defines its own `DEFAULT_CSS` frame/button block.
- [ ] Existing v0.1 EACCES/vanished-directory Pilot test
      (`tests/integration/test_panel_keys.py::test_eacces_shows_error_dialog_and_stays_in_place`)
      still passes unmodified against the rebuilt `ErrorDialog`.
- [ ] `InputDialog`: `Enter` while the `Input` has focus now submits its value (previously a no-op
      gap in the v0.1 ad-hoc version).
- [ ] `ConfirmDialog`: bare `y`/`n` and `Alt+y`/`Alt+n` both work; `Esc` → `False`.
- [ ] **Pilot test:** each of the four dialogs opened, driven via keyboard (hotkey + Enter + Esc
      paths), dismiss values asserted.

### MC-017 — Key bar (F0.14): generated from the keymap registry

**Description:**
`StatusBar` currently renders a hard-coded `HINT_ITEMS` list that has already drifted from the
real bindings (`Ctrl+T`/`Ctrl+L` shown in v0.1's stale README, removed from the keymap in v0.1's
retrofit; F5/F6/F7/F8 shown as if they worked, when they're still unbound no-ops until v0.4/v0.6).
Generate the 10 key-bar slots from `Keymap.bindings_for_context(context)` so this can't drift
again.

**What needs to be done:**
- `mycom/keymap.py`: give every `Command` a `slot: int | None` field (1-10, FAR's F1-F10
  convention; `None` for actions with no key-bar presence) — set for the currently-relevant
  actions (`help`→1, `view`→3, `edit`→4, `copy`→5, `move`→6, `mkdir`→7, `delete`→8, `quit`→10);
  actions with no slot (`switch_panel`, `panel_swap`, the sort/view/resize keys, etc.) stay
  key-bar-invisible, matching FAR's own key bar (which shows F1-F10 only).
- `Keymap.key_bar_slots(context) -> list[tuple[int, str, str] ]`: returns `(slot, key_label,
  action_label)` for each of the 10 slots in a context, `("", "")` for unassigned ones — "empty,
  not stale" per F0.14's acceptance box.
- Rewrite `StatusBar` (rename usage stays `StatusBar`, matches architecture.md's "key bar") to
  build its 10 slots from `Keymap.key_bar_slots("panel")` instead of the hard-coded `HINT_ITEMS`;
  takes the app's `Keymap` instance (or the resolved slot list) as a constructor/update argument.
- Mouse click on a slot triggers the corresponding action (`on_click` on each slot `Static`,
  looked up by slot index, calling `self.app.run_action(action_name)` — Textual's standard
  programmatic action dispatch, works for both `App.bind`-registered and `on_key`-intercepted
  actions since `run_action` goes through the same resolution `on_key`'s handlers call directly
  for the three intercepted ones — wire a small `MyComApp.run_action` awareness note if needed, or
  have the intercepted three call their `action_*` equivalents directly so a click behaves
  identically to the key).
- All key-bar CSS references `$keybar-number-bg/fg`, `$keybar-label-bg/fg` (MC-014) — zero literal
  hex.

**Dependencies:** MC-014

**Expected result:**
The key bar can never show a label that doesn't match a real binding, because it's generated from
the same registry that creates the binding.

**Acceptance criteria:**
- [ ] Key-bar labels for panel context match `Keymap.resolve(action)` for every assigned slot.
- [ ] Slots with no assigned action render empty (no ghost `Ctrl+T`/`Ctrl+L`-style labels).
- [ ] Clicking the "5Copy" slot invokes the same handler `F5` would (both currently no-ops until
      v0.4 — assert the same `run_action`/method is reached, not a visible copy operation).
- [ ] **Unit test:** `key_bar_slots` generation — every slot 1-10 accounted for, assigned ones
      match `DEFAULT_COMMANDS`, unassigned ones are empty.
- [ ] **Pilot test:** clicking a key-bar slot reaches the same action as its keyboard shortcut.

### MC-018 — Panel footer: item count, selection placeholder, free space placeholder

**Description:**
v0.1's panel footer (added mid-phase for MC-012's truncation requirement) shows item count and the
cursor row's full name. The architecture's reference layout footer format is `"3 items, 1 selected
(2.1 KB)"` plus a free-space figure in the passive panel — complete the footer to that shape now
that the layout is settled, with honest placeholders for the two pieces that don't have real data
yet (selection model is v0.3, free-space query is unscoped for v0 — decision:
[feature-coverage.md](../../feature-coverage.md) Part 3 already owns "free space placeholder").

**What needs to be done:**
- `FileBrowserPanel._update_footer`: format as `"{count} items"` (unchanged from v0.1) followed by
  a selection placeholder segment `"0 selected"` (always zero — honest until v0.3 wires the real
  count) and, only for the passive (inactive) panel, a free-space placeholder segment
  (`"-- free"` — a literal placeholder string, not a real `shutil.disk_usage` call, which is
  explicitly out of scope until decided; document the placeholder clearly so it isn't mistaken for
  real data).
- Footer CSS references `$panel-fg`/`$panel-bg` (MC-014) — zero literal hex (already the case from
  v0.1, verify no regression).

**Dependencies:** MC-014

**Expected result:**
The footer shape matches the architecture reference layout; nothing in it claims to be real data
it isn't.

**Acceptance criteria:**
- [ ] Active panel footer: `"{n} items  0 selected  {cursor-name}"`.
- [ ] Passive panel footer additionally shows the free-space placeholder segment.
- [ ] **Unit test:** footer text formatting for active/passive, zero/nonzero item count.
