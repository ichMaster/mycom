# v0.1 — GitHub Issues

Issues for phase **v0.1 — Panel core retrofit** (version **v0 — MVP**), derived from the per-phase
Tasks in [roadmap.md](../../roadmap.md) (§v0.1) and the components in
[architecture.md](../../../spec/architecture.md) (App shell, Keymap & command registry, Panels,
Filesystem layer, Logging). This file is scoped to a single phase; IDs continue from the legacy
pre-pivot phase (MC-008 → **MC-009…MC-014**).

The pre-pivot codebase (`mycom/utils/keys.py`, `mycom/config.py`, `mycom/panels/`) already renders
dual panels, navigates, and sorts, but key handling is a flat action→key dict with no context, the
loaded `AppConfig.general` fields are never read by the panel, there is no keymap-driven key bar
seam, no structured logging, and the existing integration tests call panel methods directly instead
of driving them through `Pilot` key presses. This phase closes that gap and lands the two seams
every later phase reuses: the keymap registry and logging.

## v0.1 — Panel core retrofit

### MC-009 — Keymap registry with context support

**Description:**
Replace the flat `mycom/utils/keys.py` action→key dict with a real keymap registry:
`mycom/keymap.py`. One data structure maps `action → key(s) → context → label`, feeding Textual
`BINDINGS` now (panel context) and the key bar / F9 menus later (v0.2/v1.8) — so key-bar labels can
never drift from actual bindings. No hard-coded keys remain in `app.py` or any widget.

**What needs to be done:**
- `mycom/keymap.py`: a `Command` dataclass (`action: str`, `keys: tuple[str, ...]`, `context: str`,
  `label: str`) and a `Keymap` registry class built from a `DEFAULT_COMMANDS` table covering every
  v0.1–v0.3 action already known (`help`, `view`, `edit`, `copy`, `move`, `mkdir`, `delete`, `quit`,
  `switch_panel`, `open`, `go_up`, `panel_swap` = `ctrl+u`, `resize_grow` = `ctrl+right`,
  `resize_shrink` = `ctrl+left`, `view_brief` = `ctrl+1`, `view_full` = `ctrl+2`,
  `view_wide` = `ctrl+3`, `sort_name` = `ctrl+f3`, `sort_ext` = `ctrl+f4`, `sort_mtime` = `ctrl+f5`,
  `sort_size` = `ctrl+f6`), all under `context="panel"` (additional contexts arrive with viewer/
  editor/dialog in later phases — the `context` field exists now so nothing has to migrate later).
- `Keymap.resolve(action) -> str | None`, `Keymap.actions_for_key(key, context) -> list[str]`,
  `Keymap.bindings_for_context(context) -> list[tuple[key, action, label]]` (feeds Textual
  `BINDINGS` construction).
- Config `[keybindings]` overrides applied on top of `DEFAULT_COMMANDS` exactly as
  `KeyBindings` did (same override semantics, same config section name) — no config format change.
- `mycom/app.py` builds its `BINDINGS`/key dispatch from `Keymap.bindings_for_context("panel")`
  instead of the hard-coded tuples currently in `MyComApp.BINDINGS` and `on_key`.
- Delete `mycom/utils/keys.py` and `tests/unit/test_keys.py`'s subject import; port its test cases
  onto the new registry in `tests/unit/test_keymap.py`.

**Dependencies:** None

**Expected result:**
One keymap registry is the single source of truth for every key binding; `app.py` contains no
literal key strings.

**Acceptance criteria:**
- [ ] `Keymap.resolve("copy")` returns `"f5"` by default and the configured override when
      `[keybindings] copy = "..."` is set (mirrors old `KeyBindings` behavior).
- [ ] `Keymap.bindings_for_context("panel")` returns every panel-context action with its resolved
      key and label; unknown/override-only actions are not silently dropped.
- [ ] **Unit test:** resolution with no overrides, with an override, with an override for an
      unknown action (ignored, same as old `KeyBindings`).
- [ ] `mycom/utils/keys.py` no longer exists; no remaining import of it anywhere in `mycom/` or `tests/`.
- [ ] `ruff check` finds zero hard-coded key-string literals in `app.py` outside `keymap.py` itself.

### MC-010 — Wire general config into panels; structured logging

**Description:**
`AppConfig.general` (`show_hidden`, `default_sort`, `default_sort_direction`) is loaded at startup
and then ignored — `FileBrowserPanel` always starts with `show_hidden=False`,
`sort_field="name"`, ascending. Wire these three fields into panel construction, and add
env-configurable structured logging so a full-screen TUI is debuggable.

**What needs to be done:**
- `FileBrowserPanel.__init__` accepts `show_hidden: bool`, `sort_field: str`,
  `sort_ascending: bool` (derived from `default_sort_direction == "asc"`) and uses them as the
  initial state instead of the hard-coded defaults.
- `MyComApp.compose()` passes `self._config.general.show_hidden` /
  `.default_sort` / `.default_sort_direction` into both `FileBrowserPanel` constructions.
- `mycom/logging_setup.py`: `configure_logging()` reads `MYCOM_LOG_LEVEL` (default `WARNING`) and
  `MYCOM_LOG_FILE` (default: platform log dir, e.g. `~/.config/mycom/mycom.log`) and installs a
  `logging.FileHandler` with a timestamped formatter; called once from `MyComApp.__init__` before
  any other setup. Never logs to stdout/stderr (would corrupt the TUI screen).
- Invalid `default_sort` value in config (not one of `SORT_FIELDS`) falls back to `"name"` with a
  logged warning, not a crash.

**Dependencies:** MC-009

**Expected result:**
A `config.toml` edit for `show_hidden`/`default_sort`/`default_sort_direction` visibly changes
panel behavior at next start (v0.1 DoD), and app behavior is traceable via a log file.

**Acceptance criteria:**
- [ ] `AppConfig(general=GeneralConfig(show_hidden=True))` → both panels start with hidden files
      shown.
- [ ] `default_sort="size", default_sort_direction="desc"` → panels start sorted by size,
      descending.
- [ ] An unrecognized `default_sort` value degrades to `"name"` and logs a `WARNING`, never raises.
- [ ] `MYCOM_LOG_LEVEL=DEBUG` produces DEBUG-level lines in the log file; default level is `WARNING`.
- [ ] **Unit test:** config→panel wiring for all three fields; logging level/file resolution from
      env vars (tmp path, no real `~/.config` writes in tests).

### MC-011 — F0.1 navigation: panel swap, cursor-restore, EACCES dialog, resize

**Description:**
Complete F0.1's navigation acceptance criteria beyond what already works (`Tab` switch, `Enter`/
`Backspace`): `Ctrl+U` panel swap, cursor landing on the directory just left when going up,
an error dialog (instead of the current silent empty listing) on `EACCES`, and the resize task
the roadmap owns here (§v0.1 decision, [feature-coverage.md](../../feature-coverage.md) Part 3).

**What needs to be done:**
- `MyComApp.action_panel_swap` (bound to keymap action `panel_swap`): swaps `_left_panel`/
  `_right_panel` **paths and cursor positions** between the two panels (selections are out of
  scope — the selection model lands in v0.3; document this as a `# no selection yet` note, not a
  silent gap).
- `FileBrowserPanel.navigate_up()` remembers the current directory's name before moving to the
  parent, refreshes, and moves the `FileList` cursor to that name's row (falls back to row 0 if the
  name is no longer present, e.g. renamed/deleted concurrently).
- `Ctrl+PgUp` bound as an alias for `go_up` (same handler as `Backspace`).
- `list_directory` (or its panel-side caller) distinguishes `PermissionError` from an empty
  directory: `FileBrowserPanel.refresh_listing()` catches `PermissionError` from a **new**
  `list_directory(..., strict=True)` mode (or equivalent), keeps the panel on its previous path/
  listing, and the app shows a small ad-hoc error dialog (`mycom/widgets/dialog.py`, same
  ModalScreen pattern as `ConfirmDialog` — a minimal `ErrorDialog(ModalScreen[None])` with a
  message and a single OK button; it will be rebuilt on the dialog kit in v0.2 along with the
  others).
- Panel resize: keymap actions `resize_grow`/`resize_shrink` (`Ctrl+Right`/`Ctrl+Left`) cycle the
  active panel's width through `30% / 50% / 70%` (inactive panel takes the remainder); applied via
  the `Horizontal#panel-container` children's `width` styles. In-memory only for v0.1 (no state DB
  yet — restart-persistence is a v0.3 follow-on once `state.db` exists; note this explicitly in the
  issue so it isn't silently dropped).

**Dependencies:** MC-009

**Expected result:**
Every F0.1 acceptance box holds when driven from the keyboard; a permission-denied directory
surfaces an error instead of silently showing empty.

**Acceptance criteria:**
- [ ] `Ctrl+U` swaps both panels' current paths and cursor positions.
- [ ] Going up from `child/` and back into it via `Enter` restores the cursor onto `child` in the
      parent listing.
- [ ] `Ctrl+PgUp` behaves identically to `Backspace`.
- [ ] Navigating into a directory without read permission shows an error dialog and the panel stays
      on the previous path (no silent empty listing).
- [ ] `Ctrl+Right`/`Ctrl+Left` cycle the active panel through 30/50/70 width while the inactive
      panel fills the remainder.
- [ ] **Pilot test:** `Ctrl+U` swap flow, cursor-restore-on-go-up, `Ctrl+PgUp`, resize key flow —
      all driven via `Pilot.press`, not direct method calls.
- [ ] **Pilot test:** EACCES fixture (chmod 000 tmp dir) → error dialog appears, `Enter`/`Esc`
      dismisses it, panel unchanged.

### MC-012 — F0.2 view modes: Brief / Full / Wide

**Description:**
`FileList` currently renders one fixed five-column layout. F0.2 requires three named view modes —
Brief (names only, multi-column), Full (name/size/mtime), Wide (name/size) — switchable per panel
and rendered correctly at both 80 and 200 columns, plus `<DIR>` in the size column and footer
truncation for long names.

**What needs to be done:**
- `mycom/panels/views.py`: view mode as **data**, not subclasses — a `ViewMode` enum
  (`BRIEF`, `FULL`, `WIDE`) mapped to a column spec (which of name/size/modified/permissions show,
  and whether names wrap into multiple columns for Brief).
- `FileList` gains a `set_view_mode(mode: ViewMode)` that rebuilds its `DataTable` columns from the
  spec and reloads the current entries; Brief mode lays out names in as many equal-width columns as
  fit the panel width (minimum 1).
  - Update `FileBrowserPanel.refresh_listing()`: format `size` as `"<DIR>"` for directories, not `""`.
- Keymap actions `view_brief`/`view_full`/`view_wide` (`Ctrl+1/2/3`, from MC-009) bound in
  `FileBrowserPanel`, applied to the active panel only; mode stored per-panel (in-memory for v0.1 —
  same restart-persistence caveat as MC-011's resize, deferred to v0.3's state DB).
- Long names: truncate with `…` in the table cell (fits column width); the **panel footer** (new
  small `Static` docked to the bottom of `FileBrowserPanel`, replacing nothing — v0.1 had no
  footer) shows the cursor row's full, untruncated name plus item count (`"{n} items"`); selection
  summary text is a placeholder until v0.3 wires real selection.
- Column headers render in Full/Wide (not Brief, which has no per-file metadata to head).

**Dependencies:** MC-009

**Expected result:**
All three view modes render correctly at both terminal widths tested; `<DIR>` shows in the size
column; the cursor row's full name is always visible somewhere even when the table cell truncates it.

**Acceptance criteria:**
- [ ] Brief/Full/Wide each render without column overflow at 80 and 200 columns (Pilot resize or
      fixture width).
- [ ] Directories show `<DIR>` in the size column in Full and Wide modes.
- [ ] A name longer than its column truncates with `…` in the table and appears in full in the
      panel footer when the cursor is on that row.
- [ ] Broken symlink entries (`is_symlink=True`, stat failed) render without crashing the listing
      (`utils/fs.list_directory` already tolerates this — verify the view layer does too).
- [ ] **Unit test:** view-mode → column spec mapping; truncation helper (unicode-safe, doesn't
      split a multi-byte grapheme).
- [ ] **Pilot test:** `Ctrl+1/2/3` switches the active panel's view mode; inactive panel unaffected.

### MC-013 — F0.3 sorting keys and sort direction glyph

**Description:**
`operations/sort.py::sort_entries` is already a pure, dirs-first sort function reused as-is (per
architecture: "sorting stays a pure function"). What's missing is wiring it to the FAR sort keys
and showing the active sort mode/direction in the panel header.

**What needs to be done:**
- Keymap actions `sort_name`/`sort_ext`/`sort_mtime`/`sort_size` (`Ctrl+F3`/`F4`/`F5`/`F6`, from
  MC-009) bound in `FileBrowserPanel`: pressing the active mode's key again toggles direction
  (`FileBrowserPanel.set_sort` already implements this toggle — just needs the four keys wired to
  it with the correct field mapping, since `Ctrl+F6`→`size` and `Ctrl+F5`→`mtime`, matching FAR's
  historically swapped F5/F6 for size/date, per roadmap §v0.1).
- `FileList` column headers (Full/Wide modes, from MC-012) show `▲`/`▼` appended to the header of
  the currently active sort field; Brief mode has no headers so no glyph there.
- `sort_entries`'s `field="date"` naming vs. the roadmap's `mtime` wording: keep the existing
  `operations/sort.py` field name `"date"` as the internal identifier (no rename — avoid touching a
  pure, already-tested module); the keymap action `sort_mtime` maps to internal field `"date"`.

**Dependencies:** MC-009, MC-010

**Expected result:**
`Ctrl+F3/F4/F5/F6` drive the existing sort engine; the active sort mode and direction are always
visible in the panel header.

**Acceptance criteria:**
- [ ] `Ctrl+F3` sorts by name, `Ctrl+F4` by extension, `Ctrl+F5` by mtime, `Ctrl+F6` by size —
      pressing the same key again reverses direction; dirs stay grouped first in both directions.
- [ ] The header glyph (`▲`/`▼`) tracks the active field/direction and updates immediately.
- [ ] Sort stays stable and locale-independent (existing `sort_entries` unicode fixtures still pass
      unmodified — this issue does not touch `operations/sort.py` internals).
- [ ] **Pilot test:** each of the four sort keys, plus same-key-twice direction toggle, driven via
      `Pilot.press` against a mixed fixture directory (incl. unicode names).
