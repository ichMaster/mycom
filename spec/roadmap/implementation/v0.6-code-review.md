## Findings

### #1 🔴 HIGH — Unrecognized keys leak past the viewer/editor into panel actions underneath

**Failure scenario:** Open any file with `F3` (viewer) or `F4` (editor). Press a key the viewer/
editor context doesn't recognize but the *panel* context does — e.g. `+` (`select_mask`), `Ctrl+O`
(`toggle_console`), `Ctrl+H` (`toggle_hidden`), `Ctrl+U` (`panel_swap`), `Tab` (`switch_panel`), any
sort/resize/view-mode key. `ViewerScreen.on_key`/`EditorScreen.on_key` only call `event.stop()`
*after* confirming the key maps to a recognized action in their own context:

```python
def on_key(self, event) -> None:
    actions = self._keymap.actions_for_key(event.key, context="viewer")
    if not actions:
        return          # <-- doesn't stop the event; it keeps bubbling
    event.stop()
    ...
```

An unrecognized key is never stopped, so it bubbles past the (non-modal) `Screen` all the way to
`MyComApp`'s own key-binding resolution, which finds the panel-level binding and dispatches it —
**while the viewer/editor is still the visible, "active" screen.** Reproduced empirically:
pressing `+` while the viewer is open pushes the panel's mask-select `InputDialog` on top of the
`ViewerScreen`; pressing `Ctrl+O` while the editor is open pushes `_ConsoleOutputScreen` on top of
the `EditorScreen`. Some of the leakable actions are silent state mutations with no visible
feedback at all (`Ctrl+U` swaps both panels' paths/selections; `Ctrl+H` toggles the global
hidden-files flag) — the user could return to the panels and find state changed with no idea why.
This is the same class of bug as v0.5 MC-032's "bound-key double-fire risk" and is exactly what
`DialogKit.on_key`'s own doc comment already warns about for modals: *"Stop every key this dialog
handles from bubbling past it... without this, [it] also reach[es] MyComApp.on_key and trigger[s]
the panel underneath."* The viewer/editor screens never adopted that same discipline.

**Fix:** `event.stop()` unconditionally at the top of both `on_key` handlers — the screen owns
every key while it's the active view (matching `DialogKit`, `_MessageScreen`, and
`_ConsoleOutputScreen`'s existing pattern); `event.prevent_default()` + dispatch only for keys that
map to a recognized action. Unrecognized keys are now silently swallowed instead of leaking, which
is the correct behavior for a full-screen view that's supposed to own input completely.

### #2 🟠 MEDIUM — `$EDITOR`/`Alt+F4` doesn't shell-word-split a multi-word editor command

**Failure scenario:** A very common real-world `$EDITOR` convention is a command *with flags* —
`EDITOR="code --wait"`, `EDITOR="subl -w"`, `EDITOR="vim -O"`. `mycom/app.py::_run_external_editor`
does `subprocess.run([os.environ.get("EDITOR", "vi"), str(path)])` — the *entire* env var string
becomes a single `argv[0]`. `subprocess.run(["code --wait", path])` looks for a literal binary
named `"code --wait"`, which doesn't exist, so `Alt+F4` (and `editor.external_default`) fails with
"Cannot launch external editor" for any user who has configured `$EDITOR` this way — a real,
likely-to-be-hit gap in a feature this phase's own DoD calls "the permanent escape hatch."

**Fix:** `shlex.split(os.environ.get("EDITOR", "") ) or ["vi"]` — splits a multi-word command
correctly, and falls back to `["vi"]` for both "unset" and "set to empty/whitespace" (an empty
`shlex.split` result), which the naive `or` on the raw string alone wouldn't catch.

### #3 🟠 MEDIUM — Editor save doesn't pass `newline=""`, relying on `os.linesep == "\n"`

**Failure scenario:** `EditorScreen._write` calls `path.write_text(self._serialize(), encoding=
"utf-8")` with no `newline` argument, so it defaults to `newline=None` — Python's text-mode write
path performs *universal-newline translation*, replacing every `\n` in the string with
`os.linesep`. On the actual dev/CI platform (POSIX, `os.linesep == "\n"`), that translation is an
exact no-op, which is why the CRLF round-trip tests already pass and nothing is currently broken.
But it's incidental correctness, not a guarantee: on any platform where `os.linesep == "\r\n"`
(Windows), a string this code has *already* converted to CRLF via `apply_eol` (e.g.
`"one\r\ntwo\r\n"`) would have every bare `\n` inside those pairs translated *again*, corrupting
the file to `"one\r\r\ntwo\r\r\n"`. This directly undermines the phase's own DoD: *"a CRLF
round-trip produces no spurious diff."* The standard, well-known fix for writing text you've
already normalized yourself is `newline=""`, which disables the translation entirely (the same
idiom the stdlib `csv` module documents for exactly this reason).

**Fix:** `path.write_text(self._serialize(), encoding="utf-8", newline="")`.

### #4 🟡 LOW — mtime-based external-change detection can miss same-second modifications

**Failure scenario:** The external-change guard (MC-040) compares `path.stat().st_mtime` at open
against its value right before a save. Some filesystems (older HFS+, some FAT variants) only carry
one-second `mtime` resolution; if an external process modifies the file within the same second the
editor opened it, the guard would see identical timestamps and silently allow an overwrite — a
false negative. This is inherent to mtime-only change detection (the mechanism MC-040's own issue
text specifies), not an implementation mistake; a stronger guarantee would need content hashing,
which is out of scope for what this phase asked for and adds real cost (reading the file twice) for
a low-probability race. **Home:** documented MVP limitation; revisit only if it's ever actually
observed in practice (no roadmap phase currently owns "make the external-change guard
hash-based").

## Fixes applied

### Fix #1 — stop every key unconditionally in `ViewerScreen.on_key` / `EditorScreen.on_key`

**Change:** Both handlers now call `event.stop()` before checking whether the key maps to a
recognized action, matching `DialogKit`'s existing pattern. `event.prevent_default()` + dispatch
still only happens for recognized actions; unrecognized keys are now silently swallowed instead of
bubbling to the panel level.

**Regression test:** `tests/integration/test_screen_input_isolation.py` — Pilot-driven: open the
viewer, press a panel-bound key the viewer doesn't recognize (`+`/`select_mask`, `ctrl+o`/
`toggle_console`, `ctrl+u`/`panel_swap`), assert the screen stack is unchanged and no panel-level
side effect occurred (e.g. panel paths unchanged for `ctrl+u`); same three cases repeated for the
editor.

**Verification:** `pytest` green (see below) · `ruff check` clean.

**Architecture impact:** None — this brings the viewer/editor screens in line with the *existing*,
already-documented `DialogKit` input-ownership contract; no new contract, no `spec/architecture.md`
change needed.

### Fix #2 — `shlex.split` the `$EDITOR` command before launching

**Change:** `mycom/app.py::_run_external_editor` now builds `argv` via
`shlex.split(os.environ.get("EDITOR", "")) or ["vi"]` instead of treating the whole env var as a
single binary name.

**Regression test:** `tests/integration/test_editor_external_guard.py::
test_alt_f4_splits_multi_word_editor_command` — sets `EDITOR="my-editor --flag"`, asserts
`subprocess.run` was called with `["my-editor", "--flag", str(path)]`; a companion test confirms an
empty `EDITOR=""` still falls back to `["vi", str(path)]`.

**Verification:** `pytest` green · `ruff check` clean.

**Architecture impact:** None — internal implementation detail of the already-documented `$EDITOR`
escape hatch; no contract change.

### Fix #3 — `newline=""` on the editor's save write

**Change:** `EditorScreen._write` now calls
`path.write_text(self._serialize(), encoding="utf-8", newline="")`, disabling Python's universal-
newline translation so text this code has already converted to the target EOL style is written
byte-for-byte, portably.

**Regression test:** `tests/unit/test_editor_detect.py`-adjacent coverage wasn't the right home
(this is a screen-level I/O concern, not `detect.py` logic) — added
`tests/integration/test_editor_keys.py::test_write_text_uses_newline_empty_to_avoid_double_translation`,
which monkeypatches `pathlib.Path.write_text` to capture its `newline` kwarg and asserts it's `""`
on every save.

**Verification:** `pytest` green · `ruff check` clean. (The existing CRLF round-trip tests already
passed before this fix, since `os.linesep == "\n"` on the CI/dev platform made the bug inert there
— the new test asserts the *call contract*, not just platform-incidental output, so it would catch
a regression on any platform.)

**Architecture impact:** None — an internal correctness fix to the already-documented "EOL and
trailing-newline preserved byte-for-byte on save" contract; no shape change.
