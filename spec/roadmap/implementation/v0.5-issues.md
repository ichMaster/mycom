# v0.5 — GitHub Issues

Issues for phase **v0.5 — Command line, execution, cd-sync** (version **v0 — MVP**), derived from
the per-phase Tasks in [roadmap.md](../../roadmap.md) (§v0.5) and the components in
[architecture.md](../../../spec/architecture.md) (Console, PTY, and cd-sync). This file is scoped
to a single phase; IDs continue from v0.4 (MC-031 → **MC-032…MC-035**).

Implements F0.11: a command-line prompt under the panels that always shows the active panel's
directory; `Enter` hands the real terminal to the child process through a PTY (the `script(1)`
model — interactive programs like vim/htop get full control), teeing output into a bounded ring
buffer; `cd` is intercepted and never spawns a shell. `Textual.App.suspend()` is the mechanism
that hands the terminal over — it exits Textual's screen management for the duration of the `with`
block, which is exactly the "child owns the real terminal" contract this phase needs; `pty.spawn`
(stdlib) with a custom `master_read` tee is the mechanism that streams PTY output into the ring
buffer without losing the interactive passthrough.

## v0.5 — Command line, execution, cd-sync

### MC-032 — Command-line widget + cd interception

**Description:**
The command-line prompt lives under the panels (`mycom/widgets/command_line.py`), always shows
the active panel's directory, and intercepts `cd` before it ever reaches process execution
(`mycom/console/cd.py`). This issue lands the widget and the safe, spawn-free half of F0.11;
MC-034 wires real command execution on top of it.

**What needs to be done:**
- `mycom/console/cd.py`: `parse_cd(command: str) -> str | None` — returns the target path if
  `command` (stripped) is `cd`, `cd <path>`, or `cd -` (optional; `-` before any `cd` history
  exists is just treated as a literal directory name, no OLDPWD tracking needed for v0), else
  `None` (not a cd invocation — the caller runs it normally). Supports single/double-quoted paths
  and a leading `~` (`os.path.expanduser`); bare `cd` (no argument) resolves to `$HOME`. Uses
  `shlex.split` for quote-aware tokenizing; a `cd` with more than one argument after tokenizing is
  *not* intercepted (ambiguous — falls through to real execution, which will error the way a real
  shell would).
- `mycom/widgets/command_line.py`: a `CommandLine(Static)` (or `Horizontal` composing a prompt
  `Label` + `Input`) widget — prompt text is `f"{cwd} $ "` (or similar FAR-style), updated
  whenever the active panel's directory changes (a `set_cwd(path: Path)` method the app calls
  on navigation and panel-switch, matching cd-sync). Printable characters typed while a panel has
  focus route here instead of the panel's own key handling — extend `MyComApp.on_key`'s existing
  interception list: printable, non-control keys with no modifier (excluding the keys already
  claimed by panel navigation/selection) forward to the command line's `Input` and focus it;
  navigation keys (arrows, Tab, Enter used for panel `open`, Backspace for `go_up`, F-keys, Ctrl+
  combinations) stay with the panel exactly as today. `Enter` *while the command line has focus*
  submits: if `parse_cd` matches, apply directly to the active panel (`panel.navigate_to`) and
  clear the input, no subprocess, inline `ErrorDialog`-free message (a lightweight status message,
  not a modal, for an invalid `cd` target — reuse the panel's own error-dialog path via
  `panel._show_error` equivalent, or a short-lived line under the prompt) reporting the failure;
  if it's not a `cd`, MC-034 fills in the real-execution branch (this issue can leave a documented
  `TODO`-free seam — e.g. an injectable `on_execute: Callable[[str], None] | None` the app wires
  once MC-034 lands, not a literal placeholder).
- `Escape` while the command line has focus clears its text and returns focus to the active panel
  without submitting.

**Dependencies:** None

**Expected result:**
A command-line prompt always shows the active panel's directory, printable typing routes to it
without disturbing panel navigation, and `cd` (quoted paths, `~`) changes the active panel with
zero subprocess spawns.

**Acceptance criteria:**
- [ ] `cd /tmp`, `cd ~`, `cd "path with spaces"`, and bare `cd` all resolve to the right target
      with no subprocess spawned; `cd nonexistent` reports an error inline, panel unchanged.
- [ ] Typing a printable character while a panel is focused moves focus to the command line and
      inserts the character; arrow keys, Tab, Enter (panel open), Backspace (go up), and F-keys
      are unaffected and still reach the panel.
- [ ] The prompt always reflects the *active* panel's current directory, including after
      `Tab`/`Ctrl+U` panel switches.
- [ ] `Escape` clears the command line and returns focus without side effects.
- [ ] **Unit test:** `parse_cd` — quoting, `~`, bare `cd`, multi-argument fallthrough, a
      not-a-cd command returns `None`.
- [ ] **Pilot test:** typing routes to the command line; `cd` changes the active panel; Escape
      clears without navigating.

### MC-033 — Ring buffer + PTY runner core

**Description:**
The execution engine (`mycom/console/`), pure Python with no Textual dependency — mirrors
`fileops/`'s shape (a plain, directly-unit-testable core; MC-034 wires it into the app via
`App.suspend()`). Runs a shell command in a real PTY with full passthrough (`script(1)` model)
while teeing output into a bounded ring buffer.

**What needs to be done:**
- `mycom/console/ring_buffer.py`: `RingBuffer(max_lines: int = 100_000)` — appends chunks of
  bytes (`append(data: bytes)`), splitting on `\n` internally so `lines` reflects whole output
  lines; once `max_lines` is exceeded, oldest lines are dropped (a `collections.deque(maxlen=...)`
  is the natural fit) — bounded memory regardless of how much a command prints. Exposes
  `text() -> str` (decoded `errors="replace"`, joined) for `Ctrl+O` recall (MC-035) and a
  `had_output: bool` property (anything ever appended, even if since evicted) — the "Press any
  key" prompt is skipped when a command produced no output at all, per F0.11.
- `mycom/console/pty_runner.py`: `ExitInfo` (frozen dataclass: `exit_code: int`,
  `had_output: bool`); `run_in_pty(command: str, cwd: Path, on_data: Callable[[bytes], None]) ->
  int` (returns the raw exit code) — builds `["${SHELL:-/bin/sh}", "-c", f"cd
  {shlex.quote(str(cwd))} && exec {command}"]` (the `cd && exec` wrapping puts the process in the
  right directory without this module needing its own fork/chdir dance — `exec` replaces the
  subshell so no extra process lingers) and runs it via stdlib `pty.spawn(argv, master_read=tee)`,
  where `tee` wraps `os.read(fd, 1024)` and calls `on_data(data)` with everything read before
  returning it unchanged (`pty.spawn`'s own copy loop still relays it to the real terminal — the
  tee is purely an observer, never altering what the child/user sees). Returns
  `os.waitstatus_to_exitcode(status)` from `pty.spawn`'s return value.
- POSIX-only for this phase (`spec/architecture.md`: "POSIX first-class, Windows best-effort may
  lag") — `pty` is a POSIX-only stdlib module; no Windows fallback in this issue (guard with a
  clear `NotImplementedError`/platform check if `platform/` conventions call for one, matching the
  project's "platform/ is the only OS-conditional package" rule if a stub is warranted, but don't
  build a Windows PTY path now).

**Dependencies:** None

**Expected result:**
A synchronous, real-PTY command runner — any caller (a worker, or directly, since it's expected
to run during a Textual-suspended window) gets the exit code and a bounded record of everything
the command printed, and the command itself still sees a real, fully interactive terminal.

**Acceptance criteria:**
- [ ] `run_in_pty("echo hello", tmp_path, tee)` captures `b"hello\n"` via the tee callback and
      returns exit code `0`.
- [ ] `run_in_pty("pwd", tmp_path, tee)` prints `tmp_path` — proves the `cd && exec` wrapping
      actually lands the child in the right directory.
- [ ] `run_in_pty("exit 7", tmp_path, tee)` returns exit code `7`.
- [ ] A command printing 100k+ lines does not grow `RingBuffer` past `max_lines` and does not
      hang (`run_in_pty` piping a real `yes | head -n 150000`-equivalent fixture through, real
      subprocess, not mocked).
- [ ] `RingBuffer.had_output` is `False` for a silent command (`true`) and `True` for one that
      printed anything, even after eviction has dropped those exact lines.
- [ ] **Unit test:** ring buffer eviction bounds, `had_output` semantics, `run_in_pty` exit codes
      and cwd-wrapping, all against real (non-mocked) subprocess execution — no paid/networked
      call involved, so nothing here needs mocking per the project's fixtures-over-mocks rule.

### MC-034 — Wire Enter-to-execute: suspend/run/resume, exit code, panel refresh

**Description:**
Connects MC-032's command line and MC-033's PTY runner through `App.suspend()`: `Enter` on a
non-`cd` command hands the terminal to the child, streams its output live (the user watches it
run, full interactivity — vim, htop, `git rebase -i` all work because the terminal really is the
child's), and on exit restores the panels, showing `Press any key` (skipped if no output) and the
exit code if non-zero, then refreshes both panels.

**What needs to be done:**
- `MyComApp`: the `on_execute` hook MC-032 left injectable now calls `self._run_command(text)`.
  `_run_command`: `with self.suspend(): exit_code = run_in_pty(text, self.active_panel.
  current_path, self._console_buffer.append)` (`self._console_buffer` a `RingBuffer` instance
  owned by the app, created in `__init__`) — `App.suspend()` is a **synchronous** blocking call
  (its `with` block runs to completion before Textual resumes rendering), which is correct here:
  nothing else should run while the terminal is handed over. After the `with` block: if
  `self._console_buffer.had_output` (this run) print/show "Press any key" and wait for one
  keypress (a minimal `Static`+manual key wait, or a tiny dedicated screen — reuse `DialogKit`
  only if it fits without contorting it; a bespoke small screen is fine here since this isn't a
  modal *dialog* in the DialogKit sense) before restoring; if the exit code is non-zero, include
  `Exit code: N` in that same restore message. Always: clear the command-line input, refresh
  both panels (`self.active_panel.refresh_listing()`, `self.inactive_panel.refresh_listing()` —
  an external command can touch either).
- `self._driver.can_suspend` is `False` under Textual's headless test driver (confirmed by
  reading `textual/driver.py`/`headless_driver.py` directly) — `self.suspend()` raises
  `SuspendNotSupported` there, not a silent no-op. Structure `_run_command` so `self.suspend` and
  `run_in_pty` are both reachable as separately monkeypatchable seams (plain method/module-level
  lookups, mirroring the `mycom.app.execute_plan`-style monkeypatch seam v0.4's tests already use)
  so Pilot tests can fake both without needing a real suspend-capable terminal in CI.
- A command that raises before/without a valid exit (e.g. the shell itself failing to spawn) is
  vanishingly rare given `run_in_pty` always returns a `waitpid`-derived status, but wrap the
  `run_in_pty` call in `except OSError` per the v0.4 code-review precedent (an uncaught worker/
  suspend-block exception has the same "crashes the whole app" risk as v0.4 finding #1) — show a
  plain error message in the restored panel view rather than propagating.

**Dependencies:** MC-032, MC-033

**Expected result:**
`ls`, `vim file`, `htop`, and a 100k-line-output command all round-trip cleanly: full
interactivity while running, panels correctly refreshed and showing the command's effects
afterward, exit code and Press-any-key surfaced exactly per F0.11.

**Acceptance criteria:**
- [ ] A non-`cd` command executed via Enter suspends the app, runs with real terminal
      passthrough, and restores panels afterward with both refreshed.
- [ ] A silent, zero-exit command skips "Press any key"; one with output shows it; a non-zero
      exit additionally shows `Exit code: N`.
- [ ] An unexpected `OSError` around the suspend/run block shows a clean message instead of
      crashing the app (mirrors the v0.4 code-review fix).
- [ ] **Integration test (Pilot, `self.suspend` and `run_in_pty` monkeypatched to fakes):**
      Enter on a command reaches `run_in_pty` with the active panel's cwd; both panels refresh
      after; the had-output/exit-code display logic is exercised for all four combinations
      (silent+zero, output+zero, silent+nonzero, output+nonzero).
- [ ] **Unit test (real subprocess, no Textual):** the `run_in_pty` 100k-line and `vim`-shaped
      (a real but trivial full-screen-ish fixture, e.g. a script that reads one byte from stdin
      and exits) cases already covered by MC-033 stand in for the DoD's "100k-line" and rough
      interactivity checks — full `vim`/`htop` verification is explicitly a manual matrix per
      roadmap §v0.5 Tests, not automatable in CI.

### MC-035 — Ctrl+O toggle + cd-sync polish

**Description:**
`Ctrl+O` toggles between the panels and the last console output (the ring buffer's current
content) without re-running anything; cd-sync is verified both directions end-to-end (panel nav
→ prompt updates; the process cwd used by the *next* execution always matches whichever panel is
active *at Enter time*, not whichever was active when the command line was last focused).

**What needs to be done:**
- A minimal `ConsoleOutputScreen` (or reuse the same small screen MC-034 built for "Press any
  key", generalized to take arbitrary text) showing `self._console_buffer.text()`; bound to
  `Ctrl+O` via the keymap registry (`Command("toggle_console", ("ctrl+o",), "panel",
  "LastOutput")`) — pressing it again (or `Esc`) returns to the panels. Empty buffer (no command
  run yet this session) shows a plain "No output yet" message instead of an empty screen.
  `Ctrl+O` is documented as a `_INTERCEPTED_ACTIONS`-style key only if it needs to win over any
  existing binding in that slot; otherwise a normal `App.bind` entry is enough since nothing else
  currently claims `Ctrl+O`.
- Verify (and fix if found wanting) that `MyComApp.action_switch_panel`, `Ctrl+U` panel swap, and
  direct panel navigation all call `CommandLine.set_cwd` so the prompt is never stale — this is
  mostly confirming MC-032's hook is wired at every navigation call site introduced across v0.1–
  v0.4, not new logic.

**Dependencies:** MC-034

**Expected result:**
`Ctrl+O` recalls the last command's output instantly (F0.11's own acceptance criterion); the
prompt is provably never stale across every panel-changing action in the app.

**Acceptance criteria:**
- [ ] `Ctrl+O` after a command with output shows that output; pressing it again (or Esc) returns
      to the panels, unchanged.
- [ ] `Ctrl+O` with no command run yet shows a clear "no output" message, not a blank screen.
- [ ] The prompt updates immediately on `Tab` panel switch, `Ctrl+U` swap, and any panel
      navigation (`Enter` into a directory, `Backspace` up) — audited across all of v0.1–v0.4's
      navigation call sites.
- [ ] **Pilot test:** `Ctrl+O` recall round-trip; prompt-follows-active-panel across switch/swap/
      navigate.

## v0.5 scope notes

**Total effort:** ~2.5 weeks (3 M + 1 S).
**Critical path:** `MC-032`/`MC-033` (parallelizable) → `MC-034` → `MC-035`.
**Phase DoD (roadmap §v0.5):** `vim file` round-trips cleanly back to panels showing the new
mtime; `cd /tmp` is instant with no spawn; a 100k-line command neither hangs nor exhausts memory.
**Contracts pinned this phase:** `mycom/console/`'s `RingBuffer`/`run_in_pty`/`parse_cd` are new,
pure, Textual-free seams (mirroring `fileops/`'s shape) — already anticipated in
`spec/architecture.md` §Console, PTY, and cd-sync, so no doc change needed beyond what this phase
implements. `App.suspend()` (Textual's own API) is the mechanism that hands the terminal to the
child — not a new seam MyCom defines, just the correct existing tool for this contract.
**Mock note:** no paid APIs or `claude` binary this phase. `run_in_pty` tests run real (trivial,
non-interactive) subprocesses — `echo`, `pwd`, `exit N`, a bounded-output generator — never
mocked, per `spec/architecture.md` §Testing and CI. Full interactive-program verification (vim,
htop under tmux) is an explicit **manual matrix**, not part of the automated suite, per roadmap
§v0.5 Tests — this is a deliberate, spec'd scope boundary, not a gap.
